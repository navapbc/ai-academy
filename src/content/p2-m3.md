# Advanced Prompt Patterns

A model's output quality is not fixed. Given the same underlying model, a well-structured prompt can produce research-grade analysis while a vague prompt produces a generic paragraph. Understanding and applying prompt patterns is one of the highest-leverage skills in practical AI work — it costs nothing extra and compounds across every task you use AI for.

> **Core insight:** You are not just asking a question. You are configuring a reasoning system. The structure, examples, constraints, and persona you provide all shape what the model does with your request.

## Zero-Shot Prompting

**Zero-shot prompting** means asking the model to perform a task with no examples — just an instruction. It is the default mode most people use.

```
Summarize the following policy document in three bullet points.

[document text]
```

Zero-shot works well for general tasks (summarization, translation, reformatting) where the desired output format is obvious. It tends to break down for tasks requiring consistency across many outputs, or where the output format is unusual.

## Few-Shot Prompting

**Few-shot prompting** means providing 2–5 examples of input/output pairs *before* the real task. It is the single most reliable pattern for achieving consistent, formatted output.

```
Below are examples of how to classify a benefit program inquiry:

Input: "How do I apply for food stamps?"
Category: SNAP Application Process

Input: "My renewal was denied, what can I do?"
Category: Appeals and Reconsideration

Input: "Do I qualify if I'm self-employed?"
Category: Eligibility Determination

Now classify this inquiry:
Input: "When does my WIC voucher expire?"
Category:
```

The model learns the format, the vocabulary, and the level of specificity from the examples — without any formal training. At Nava, few-shot prompting is the standard pattern for any task that will run at volume or be executed by multiple people who need to produce consistent outputs.

## Chain-of-Thought (CoT) Prompting

**Chain-of-Thought (CoT)** prompting elicits explicit reasoning by asking the model to think through a problem before producing its final answer. The key phrase is: **"Think step by step."**

```
A state agency wants to determine if a household of 3 with a monthly gross income
of $2,800 qualifies for SNAP. The federal poverty level for a household of 3 is
$2,072/month, and the SNAP gross income limit is 130% FPL.

Think step by step, then give your final answer.
```

Without CoT, the model might jump to an answer and get arithmetic wrong. With CoT, it walks through the calculation, catching errors along the way. CoT is most valuable for multi-step reasoning, policy interpretation, or any task where the path to the answer matters, not just the conclusion.

### When to use CoT

- Policy interpretation with multiple eligibility conditions
- Reviewing a process flow for logical gaps
- Debugging a technical implementation step-by-step
- Any task where you need to audit the model's reasoning

## Role Prompting

**Role prompting** establishes the model's identity, expertise level, and implied constraints before the task begins.

```
You are a senior policy analyst specializing in federal-state Medicaid partnerships.
You write clearly for a professional audience of state health agency staff.
You cite specific regulatory sections when relevant.
```

A well-defined role affects tone, vocabulary, level of detail, and what the model treats as implicit background knowledge. Setting a role as a "senior policy analyst" vs. "plain language writer" will produce noticeably different prose from the same underlying model.

## Output Constraints

**Output constraints** force the model into a specific structural format. This is critical for any AI output that will be consumed by another system, displayed in a UI, or compared across multiple runs.

### JSON output
```
Return your analysis as a JSON object with the following keys:
- "summary": string (1-2 sentences)
- "risk_level": one of ["low", "medium", "high"]
- "recommended_action": string
- "confidence": number between 0 and 1

Return only the JSON. No preamble or explanation.
```

### Markdown table
```
Format your output as a Markdown table with columns:
| Policy Section | Plain Language Summary | Applicant Action Required |
```

Without explicit output constraints, models tend to produce free-form prose. In production AI pipelines, unpredictable output formats break downstream parsing. Define the format in the prompt.

## Self-Consistency

**Self-consistency** is a technique for improving reliability on high-stakes single questions: run the same prompt three times (with temperature > 0 to introduce variation) and take the majority answer.

If all three runs produce the same answer, confidence is high. If they diverge, that is a signal the question is ambiguous, the model is uncertain, or the grounding context is insufficient. Self-consistency is especially useful for policy interpretation questions where a wrong answer has consequences.

## The ReAct Pattern (Reason + Act)

**ReAct** is an agent-level pattern that alternates between **reasoning** (thinking about what to do next) and **acting** (calling a tool or taking a step). It powers most modern AI agents. Understanding it helps you reason about what an agent is doing under the hood — and where it can go wrong — even if you are not building agents yourself.

## Context Engineering vs. Prompt Engineering

These terms are often conflated but address different problems:

| Concept | Focus | Question it answers |
|---|---|---|
| **Prompt engineering** | How you ask | What instruction, format, or examples produce the best output? |
| **Context engineering** | What information you provide | What documents, data, and background does the model need to reason well? |

Most prompt failures at Nava are actually context failures — the model gave a mediocre answer not because the instruction was poorly worded, but because the relevant policy document, data table, or background fact was missing from the context.

## The Nava Prompt Template

For policy and research tasks, Nava uses a standard three-part prompt structure:

```
## ROLE
You are a [role description]. You write for [audience]. You follow [constraints].

## CONTEXT
[Grounded documents, data, or background information]

## TASK
[Specific instruction with output format constraint]

[User's question or input]
```

This structure keeps prompts auditable, reusable, and easy to hand off — a colleague receives a complete, self-contained prompt rather than trying to reconstruct it from memory.

### Worked Example: Policy Summarization

```
## ROLE
You are a plain language specialist working for a state Medicaid agency.
Your audience is caseworkers with a high school education.
Do not use legal jargon without immediately defining it.

## CONTEXT
[Section 4.2 of the 2024 Medicaid State Plan Amendment, 847 words]

## TASK
Summarize the key changes in Section 4.2 as a bulleted list.
Each bullet should be one sentence. Maximum 6 bullets.
Use plain language (8th-grade reading level).
At the end, add a one-sentence note on any action caseworkers must take.
```

## Common Anti-Patterns

- **Vague instructions:** "Write something about SNAP" → no output format, no audience, no length target.
- **No output format:** The model chooses a format. It will be different every time.
- **Multiple questions in one prompt:** "Summarize this AND compare it to last year's AND recommend next steps" → the model addresses all three poorly rather than one well.
- **Assuming shared context:** "Make it better" is meaningless without specifying what "better" means in this context.
- **Ignoring the role:** Skipping a role prompt for a specialized task means the model defaults to a generic helpful assistant rather than a domain expert.

## Prompt Versioning

Treat prompts like code. A prompt that produces good results today is an asset — it should be:

- Stored in version control alongside the code that calls it
- Labeled with a version number or date
- Tested against a set of representative inputs with documented expected outputs
- Reviewed and updated when the underlying policy or task changes

At Nava, prompt files live in the same repository as the product they power. If a prompt changes, that change is reviewed, tested, and committed — not quietly edited in a shared doc.

## Key Takeaways

1. Few-shot prompting is the most reliable pattern for consistent, formatted output at volume.
2. Chain-of-Thought unlocks multi-step reasoning — use it for policy interpretation and complex analysis.
3. Always define an output format constraint in prompts that feed into pipelines or reports.
4. Most prompt failures are context failures — the information the model needed was simply not provided.
5. Version-control your prompts. A prompt is a production artifact, not a throwaway query.
