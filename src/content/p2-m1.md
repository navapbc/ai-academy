# The Art of Grounding

Large language models are trained on a static snapshot of text data. Once training ends, their internal knowledge freezes. They have no awareness of anything that happened afterward — a regulatory change published last month, a new CMS guidance letter, or an updated state Medicaid waiver. This is the **knowledge cutoff problem**, and it is one of the most practically important limitations for govtech work.

> **Key rule:** An ungrounded model answering questions about recent policy is not making things up on purpose — it is confidently extrapolating from outdated information. The output can look authoritative while being completely wrong.

## What Is Grounding?

**Grounding** means providing the model with a specific piece of text — a document, a policy excerpt, a data record — and instructing it to treat that text as its *only* source of truth for a given query. Instead of drawing on its training weights, the model reads and reasons over the material you supply.

Grounding is not the same as fine-tuning, and understanding that difference is essential for practical AI work.

### Grounding vs. Fine-Tuning

| Dimension | Grounding | Fine-Tuning |
|---|---|---|
| How it works | Injects text at query time | Changes the model's weights |
| Speed | Seconds | Hours to days |
| Cost | Negligible (just tokens) | Significant compute spend |
| Flexibility | Swap the document anytime | Requires retraining to update |
| Risk | Low — no model changes | Higher — can degrade base capabilities |

For the vast majority of Nava use cases, grounding is the right tool. Fine-tuning is reserved for situations where you need the model to consistently adopt a highly specialized vocabulary or behavior that cannot be achieved through prompting alone.

## Context Windows and Token Limits

Every LLM has a **context window** — the maximum amount of text it can "hold in mind" at one time, measured in **tokens** (roughly 0.75 words per token in English). Modern models range from ~8,000 tokens (small/fast) to 200,000+ tokens (large/slow).

When you ground a model, the document text consumes a portion of that window. Here is a rough budget to keep in mind:

```
Context window = system prompt + grounding documents + conversation history + user question + model response
```

### What Happens When You Exceed the Limit

If the total token count exceeds the context window, the provider's API will return an error, or the model will silently truncate earlier content. In practice this means the beginning of a long document may be dropped — often the section that contained the most critical definitions. This is called **context overload** and it is one of the most common grounding mistakes.

**Mitigation:** Chunk your documents (see RAG below) rather than injecting entire files.

## RAG: Retrieval-Augmented Generation

**RAG (Retrieval-Augmented Generation)** is the standard architecture for grounding at scale. Instead of stuffing an entire document library into every prompt, RAG retrieves only the most relevant sections and injects those.

The pipeline has four stages:

### Stage 1 — Chunking
Split source documents into segments, typically 300–800 tokens each. Chunk boundaries should respect natural units: paragraphs, policy sections, table rows. Poorly chosen chunk boundaries split sentences mid-thought and degrade retrieval quality.

### Stage 2 — Embedding
Pass each chunk through a **vector embedding model** — a neural network that converts text into a high-dimensional numerical array (a vector). Semantically similar chunks end up close together in this high-dimensional space. Store these vectors in a **vector database** (e.g., pgvector, Chroma, Weaviate).

### Stage 3 — Retrieval
At query time, embed the user's question using the same model. Perform a **similarity search** (typically cosine similarity) to find the chunks whose vectors are nearest to the query vector. Return the top-K results (commonly K = 3–8).

### Stage 4 — Injection
Prepend the retrieved chunks to the prompt, followed by the user's question. The model answers using only the provided material.

```
[System prompt: answer only from the provided context]
[Retrieved chunk 1 — policy section 4.2]
[Retrieved chunk 2 — FAQ item 17]
[Retrieved chunk 3 — eligibility table row]

User question: What changed for applicants after the 2024 waiver amendment?
```

## Semantic Search vs. Keyword Search

Traditional keyword search matches exact words. A query for "claimant changes" finds only documents containing those specific words.

**Semantic search** operates on meaning. The embedding of "what changed for people applying for benefits" is mathematically close to chunks about "applicant eligibility updates" even though none of those words overlap. This makes RAG dramatically more robust for policy Q&A, where users phrase questions in plain language while documents use regulatory terminology.

## The Grounding Prompt Pattern

When grounding a model, the system prompt must establish a clear epistemic boundary. A reliable pattern used at Nava:

```
You are a policy assistant. Answer the user's question using ONLY the information
in the "CONTEXT" section below. If the answer cannot be found in the context,
respond with: "I don't have enough information to answer that question."
Do not use outside knowledge. Do not speculate.

CONTEXT:
---
[retrieved document chunks go here]
---
```

The phrase "Based on the following text ONLY" (or equivalent) is load-bearing. Without it, models tend to blend grounding material with their training knowledge, producing responses that are partially accurate and difficult to audit.

## Worked Example: Medicaid Waiver Q&A

**Ungrounded query:**
> "What are the new income limits under the 2024 Medicaid expansion waiver?"

The model will answer from training data. If the waiver was published after its cutoff — or if the state-specific details were simply not well-represented in training — the answer will be wrong, confidently stated.

**Grounded query:**
The actual waiver text is chunked, embedded, and stored. At query time, the relevant income-limit section is retrieved and injected:

```
CONTEXT:
Section 3.1: Effective January 1, 2024, the modified adjusted gross income (MAGI)
threshold for single adults is raised to 138% of the Federal Poverty Level (FPL).
Households with a pregnant member qualify at 213% FPL...

User: What are the new income limits?
```

The model now reads and summarizes the actual regulatory text. If the user asks about a detail not present in the retrieved chunks, a properly prompted model says "I don't have enough information" rather than fabricating a number.

## Common Grounding Mistakes

- **Context overload:** Injecting entire PDFs instead of relevant chunks. Wastes tokens, buries the signal.
- **Stale documents:** The grounding database is not updated when policy changes. The model is "grounded" but to outdated truth.
- **Chunks that are too large:** A 2,000-token chunk containing five policy topics dilutes retrieval relevance — you get a lot of irrelevant text alongside the answer.
- **No fallback instruction:** Without explicit "say I don't know" instructions, models speculate rather than admit ignorance.
- **Ignoring chunk boundaries:** Splitting in the middle of a definition or table renders the chunk uninterpretable.

## Key Takeaways for Nava Work

1. Always use grounding when answering questions about specific policies, regulations, or client-specific data.
2. Treat the grounding document as the authoritative source — not the model's training knowledge.
3. If the relevant information is not in the grounded context, the model **must** say "I don't know."
4. RAG is the production-grade solution; direct injection works for prototyping or small documents.
5. Version-control your grounding documents the same way you version code — know which policy text was active when a query was answered.

## Nava Research: Hybrid Chunking in Production

Nava's Labs team ran a direct experiment on chunking strategies while building the benefits navigator chatbot. The requirement was strict: caseworkers needed accurate answers *and* readable source citations within a 2-minute interaction window.

They tested three approaches:

### Experiment 1 — Fixed-Length 500-Word Chunks
Optimized for LLM accuracy, but the citations were unreadable — long, context-stripped fragments that caseworkers couldn't verify quickly.

### Experiment 2 — Paragraph-Based Chunks
Better citation readability, but answer quality degraded because the LLM was working with smaller, less contextualized inputs.

### Experiment 3 — Hybrid Approach (Optimal)
- **Longer chunks** (full policy sections) fed to the LLM for answer generation — preserving context and accuracy
- **Shorter sub-chunks** (paragraph-level) extracted from the matched section for the citation displayed to the user — readable and verifiable
- **Metadata** (section headings, document titles) attached to each chunk to enhance retrieval relevance

**The key insight from this research:** separate what you give the algorithm from what you show the end user, and optimize each independently.

The LLM needs enough context to reason accurately — longer chunks gave it more signal and produced better answers. The caseworker needs a tight, scannable citation they can verify in seconds — paragraph-length sub-chunks served that purpose. These are different requirements and they call for different chunk sizes.

### Implications for Your RAG Implementations

When building a grounded system at Nava:
- Don't use a single chunk size for everything — use larger chunks for LLM input, smaller sub-chunks for display
- Always attach source metadata (document name, section heading, date) to every chunk
- Test citation readability with actual end users — not just answer accuracy with technical evaluators
