# The Local Stack

Running AI models directly on your own hardware — rather than sending data to a cloud provider — is the foundation of privacy-safe AI in government work. This module explains why local models exist, how the key tools work, and how to choose the right model for govtech tasks at Nava.

---

## Why Local Models Exist

Cloud AI services like OpenAI, Anthropic, and Google are powerful, but they come with real tradeoffs for government work:

- **Privacy risk**: Every prompt you send to a cloud API leaves your network. For claimant data, PII, or sensitive case details, that is often unacceptable — and sometimes legally prohibited.
- **Cost at scale**: API pricing adds up fast when processing thousands of documents or running long reasoning chains.
- **Latency**: Round-trip calls to remote servers add delay — especially for real-time or interactive workflows.
- **Offline capability**: Field offices, air-gapped systems, and low-connectivity environments need AI that works without internet access.

Local models solve all four problems. The tradeoff is that they require more setup and run on your own hardware — but for Nava's govtech work, that tradeoff is often the right call.

---

## Ollama: Docker for AI Models

**Ollama** is an open-source tool that makes running large language models locally as simple as running a container. Think of it as Docker for AI — it handles model downloads, versioning, and serving via a local REST API.

### How Ollama Works

Ollama downloads **GGUF model files** to your local machine and exposes a REST API on `localhost:11434`. You interact with your model the same way you would call any web API. No accounts, no API keys, no data leaving your machine.

### Key Commands

```bash
# Pull a model (downloads it to your machine)
ollama pull mistral

# Run a model interactively in the terminal
ollama run llama3

# List all downloaded models and their sizes
ollama list

# Remove a model to free disk space
ollama rm mistral
```

### The `/api/chat` Endpoint

For multi-turn conversations in your applications, use the chat endpoint directly:

```bash
curl http://localhost:11434/api/chat -d '{
  "model": "llama3",
  "messages": [
    { "role": "system", "content": "You are a plain-language policy assistant." },
    { "role": "user", "content": "Summarize the key eligibility rules in this excerpt." }
  ],
  "stream": false
}'
```

The `messages` array supports full conversation history — pass prior turns to maintain context across a session. This makes it easy to build multi-turn assistants on top of any local model.

## LM Studio: GUI-Based Local AI

**LM Studio** is a desktop application for running local models with a graphical interface — no terminal required. It is ideal for non-technical teammates who want local AI without command-line setup.

### Key Features

- Browse and download models from Hugging Face directly in the app
- Load a model and enable the **local server** on port `1234`
- Exposes an **OpenAI-compatible API** — any code written for the OpenAI SDK works with LM Studio by changing one base URL

```python
from openai import OpenAI

# Point at LM Studio instead of OpenAI — one line change
client = OpenAI(base_url="http://localhost:1234/v1", api_key="lm-studio")

response = client.chat.completions.create(
    model="local-model",
    messages=[{"role": "user", "content": "Draft a plain-language benefits summary."}]
)
print(response.choices[0].message.content)
```

> **Key insight**: The OpenAI-compatible interface means you can prototype with cloud APIs and swap to a local model for production with a single config change — no code rewrite needed. This is a powerful pattern for Nava teams building govtech tools.

## GGUF Format and Quantization

**GGUF** (GPT-Generated Unified Format) is the standard file format for locally-run models. It packages model weights and metadata into a single portable file — easy to share, version, and download.

**Quantization** compresses model weights to reduce file size and memory requirements. A 7-billion-parameter model that would normally require ~14 GB of RAM can be reduced to ~4 GB with 4-bit quantization, with a moderate quality tradeoff.

### Common Quantization Levels

| Level | Approx. Size (7B model) | Quality | Speed |
|-------|------------------------|---------|-------|
| `Q4_K_M` | ~4 GB | Good | Fastest |
| `Q5_K_M` | ~5 GB | Better | Fast |
| `Q8_0` | ~8 GB | Best | Slower |

For most govtech tasks — summarization, classification, extraction — `Q4_K_M` is sufficient and the practical default. Use `Q8_0` when you need maximum accuracy on complex legal or policy reasoning.

## Hardware Guide

You do not need a supercomputer to run useful local models. Here is what different hardware configurations can handle:

| RAM | Recommended Models | Notes |
|-----|--------------------|-------|
| 8 GB | phi3:mini, gemma2:2b | Fast for simple tasks; limited headroom |
| 16 GB | llama3:8b, mistral:7b | The sweet spot for most Nava workflows |
| 32 GB+ | 30B+ models | High-quality reasoning at scale |

### GPU Acceleration

- **Apple Silicon (M1/M2/M3/M4)**: Excellent local AI performance. Metal GPU acceleration is built in — Ollama uses it automatically. A MacBook Pro M3 runs `llama3:8b` at conversational speeds without configuration.
- **NVIDIA GPU (CUDA)**: Fastest inference available for dedicated AI workstations. An RTX 3090 or 4090 with 24 GB VRAM can run 30B+ models at real-time speeds.
- **CPU-only (Intel/AMD)**: Works for smaller models (3B–7B) but noticeably slower. Still viable for background batch processing where latency is not critical.

## Model Selection for Govtech

Not all models are equally suited for government work. Here are the recommended choices at Nava:

### `phi3:mini` (Microsoft)
- ~2.3 GB, very fast, runs on 8 GB RAM
- Best for: summarization, short-form classification, quick data extractions
- Limitation: weaker on multi-step reasoning and long documents

### `llama3:8b` (Meta)
- ~4.7 GB, excellent reasoning for its size
- Best for: complex analysis, structured output, policy Q&A, instruction following
- **The default recommendation for most Nava tasks**

### `mistral:7b` (Mistral AI)
- ~4.1 GB, fast, strong instruction following
- Best for: document drafting, data extraction, structured tasks with clear schemas
- Good alternative when llama3 is too slow on lower-powered hardware

### `granite3.1-dense` (IBM)
- Designed specifically for enterprise and professional tasks
- Strong on structured data, compliance language, and business-style documents
- A natural fit for Nava's government-facing program work

## The Core Tradeoff

Local models are roughly 1–2 generations behind frontier cloud models like GPT-4o or Claude Sonnet. They make more errors on complex multi-step reasoning, produce less polished prose, and have smaller context windows.

> **But they are good enough for 80% of govtech tasks** — and for any task touching sensitive data, "good enough locally" is the right call over "better but risky in the cloud."

The skill in local AI is matching the right model to the right task: use cloud AI where it is safe and the additional capability is genuinely needed, and run local where privacy, cost, or offline access matter. Most of Nava's day-to-day AI work falls squarely in local territory.

## Key Takeaways

- Ollama is the fastest path to a local model; `ollama run llama3` is a single command
- LM Studio provides an OpenAI-compatible API with a GUI — great for non-engineers on your team
- Quantization (Q4/Q5/Q8) controls the size-vs-quality tradeoff; `Q4_K_M` is the practical default
- 16 GB RAM + Apple Silicon is the current sweet spot for Nava laptops
- Model choice matters: match the model to the task type, not just what is popular
- The local-vs-cloud decision is primarily a **data sensitivity decision**, not a capability decision
