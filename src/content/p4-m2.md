# Advanced Tooling & Agents

So far in this course, AI has been a text-in, text-out system. You write a prompt, the model writes a response. That model is powerful — but it is blind, stationary, and amnesiac. It cannot look at a file, run a calculation, check a database, or take an action in the world. The next generation of AI systems breaks that limitation through **tool use** and **agent architectures**.

> **Key shift:** A model that can only generate text is a writer. A model that can call tools is a collaborator. A model that can chain tool calls across steps is an agent.

## The Tool Use Paradigm

**Tool use** (also called **function calling**) gives a model the ability to request that an external piece of code be executed. The model doesn't run the code itself — it produces a structured description of what it wants to call, your application runs it, and the result is fed back into the conversation.

The cycle looks like this:

```
1. User asks a question
2. Model decides it needs a tool (e.g., "search the policy database")
3. Model outputs a structured JSON call:
   { "tool": "search", "query": "SNAP income limits 2025" }
4. Your application executes the search
5. Results are appended to the conversation as a "tool result" message
6. Model reads the result and produces its final response
```

This is not the model browsing the internet freely. Every tool is explicitly defined by the developer, with a name, description, and typed parameters. The model can only request tools you have given it.

### Why This Matters for Govtech

Without tool use, an AI assistant can only work with what you paste into the prompt. With tool use, it can look up a client's current case status, retrieve the applicable regulation section, check whether a form version is current, and calculate income ratios — all within a single conversation.

## MCP: Model Context Protocol

**MCP (Model Context Protocol)** is an open standard published by Anthropic in late 2024. It standardizes the interface between AI models and external systems — file systems, databases, APIs, calendars, search engines — the same way HTTP standardized communication between web browsers and servers.

### Architecture

MCP uses a **server-client model**:

- **MCP servers** expose a set of tools and resources. A file-system server exposes `read_file`, `write_file`, `list_directory`. A database server exposes `query` and `insert`. A calendar server exposes `list_events` and `create_event`.
- **MCP clients** (the AI model's host application) connect to those servers and make the available tools visible to the model.

```
[AI Model]
    ↕  (MCP client protocol)
[MCP Host App]
    ↕  (MCP server protocol)
[File System] [Database] [Internal API] [Calendar]
```

### Local MCP Servers

A critical advantage for govtech: **local MCP servers run entirely on your machine**. No data leaves your network. You can give a local Ollama model access to a folder of sensitive policy PDFs through a local MCP file-system server, and the entire interaction — model inference, file reads, query results — stays on-premise.

This is the architecture that makes local-first AI viable for FISMA-regulated environments. The model is local. The tools are local. The data never travels.

### Practical MCP Servers Available Today

| Server | What It Exposes | Govtech Use Case |
|---|---|---|
| `filesystem` | Read/write local files and directories | Query a folder of policy PDFs |
| `sqlite` | Read/write a local SQLite database | Case management data lookup |
| `fetch` | HTTP GET requests | Pull from an internal intranet API |
| `git` | Read git history, diffs, commits | Audit prompt version history |
| `puppeteer` | Control a headless browser | Automated accessibility screenshots |

## Code Interpreters

Some models can not only call tools — they can write and execute code. **Code interpreter** mode gives the model a sandboxed Python environment where it can run arbitrary computation, inspect results, and iterate.

This unlocks a qualitatively different category of tasks:

**Data analysis.** "Here is a CSV of 40,000 benefit applications from the last fiscal year. What demographic patterns appear in denial rates by county?" The model writes a pandas script, runs it, reads the output, and produces a plain-language analysis — without the data ever leaving the local sandbox.

**Report generation.** "Generate a policy compliance report comparing our current implementation against the checklist in section 4 of the attached CMS guidance." The model parses both documents, writes comparison logic, and outputs a structured report.

**Calculation verification.** "Given these household characteristics, calculate MAGI under the current rulebook and confirm whether the system's eligibility determination was correct." The model writes the calculation explicitly, making the logic auditable.

## Multi-Modal Models

Modern frontier models — and a growing set of local models — can process more than text. **Multi-modal** models accept images, PDFs, and audio as inputs alongside text.

### Vision

Feed a model a screenshot of a government form UI and ask: "Does this error message meet WCAG 2.1 contrast ratio requirements?" The model inspects the image, reasons about the visual contrast, and flags violations.

A local vision model like **LLaVA** or **moondream** can run this check on a folder of UI screenshots without sending a single pixel to a third-party API.

### OCR and Document Extraction

Scanned government forms are a constant challenge in eligibility systems. A multi-modal model can extract structured data directly from a scan — reading field labels and handwritten or typed values — replacing brittle OCR pipelines with a single model call.

### Audio Transcription

Models like **Whisper** (local, open-source) transcribe audio to searchable text. Use case: a hearing recording from an appeals process is automatically transcribed and indexed, allowing case managers to search for relevant testimony across hundreds of recordings without manual review.

## RAG with Local Models

Recall from Module 1 that RAG (Retrieval-Augmented Generation) is the standard pattern for grounding a model in a specific document set. The local-first version of this stack combines three components:

| Component | Tool | Role |
|---|---|---|
| Embedding model | `nomic-embed-text` via Ollama | Converts text chunks to vectors |
| Vector database | ChromaDB (runs locally) | Stores and searches vectors |
| Generation model | Any Ollama model | Reads retrieved chunks, generates answer |

```
# Minimal local RAG setup (conceptual)

1. ollama pull nomic-embed-text
2. pip install chromadb
3. Chunk your policy PDFs → embed each chunk → store in Chroma
4. At query time:
   - Embed the user's question with nomic-embed-text
   - Search Chroma for the top-5 most similar chunks
   - Inject those chunks into the Ollama model prompt
   - Return the grounded answer
```

Every step in this pipeline runs on your laptop or on-premise server. A caseworker's query against a Medicaid policy knowledge base never touches the internet.

## Microsoft Semantic Kernel

For teams building production-grade AI applications in the Nava enterprise context, **Semantic Kernel** is worth knowing. It is Microsoft's open-source SDK (available in Python, C#, and Java) for orchestrating AI agents with tools, memory, and planning.

Semantic Kernel provides:
- A unified interface for calling different LLM providers (Azure OpenAI, local Ollama, Anthropic)
- A **plugin** system for defining tools in a structured, reusable way
- **Planner** components that break a high-level goal into a sequence of tool calls automatically
- Memory connectors for persistent vector stores

For a Nava team building a multi-step benefits navigator on Azure Government cloud, Semantic Kernel is a reasonable production choice. For a local-only prototype, direct Ollama + LangChain integration is simpler.

## Emerging Govtech Agent Patterns

These are agent architectures that are technically feasible today and directly relevant to Nava project work.

### Policy Change Monitor

An agent that watches a set of regulatory sources (CMS, HHS, state Medicaid agency bulletin feeds), detects when new guidance is published, extracts the diff from the previous version, and produces a plain-language summary of what changed and what teams need to review. Human policy analysts review the summaries rather than doing the initial scanning themselves.

### Accessibility Auditor Agent

A multi-step agent that: (1) takes a URL or a folder of screenshots, (2) runs each through a vision model to identify potential WCAG violations, (3) cross-references findings against a WCAG 2.1 checklist, (4) produces a structured report with issue severity, location, and suggested fix. Human reviewers validate flagged issues rather than performing full manual audits from scratch.

### Benefits Navigator

A multi-step agent that: (1) collects household characteristics through a structured interview, (2) queries each relevant program's eligibility rules via tool calls, (3) determines likely eligibility for each program, (4) generates a plain-language explanation of findings and next steps, (5) flags any ambiguous determinations for caseworker review. The agent does not make final determinations — it surfaces a structured assessment for human decision.

## The Non-Negotiable Safety Guardrail

Agents can act quickly, at scale, across multiple systems. That is exactly what makes them dangerous without human oversight.

> **The Nava rule for agent output:** Any automated agent output that will be presented to a citizen, used to make a case decision, or sent to a government partner must be reviewed by a human before delivery. No exceptions.

This is not a temporary rule while the technology matures. It is a structural requirement of working in civic tech, where a wrong answer has real consequences for people's access to housing, health care, and food assistance. The agent's job is to do the labor of first-pass research and synthesis. The human's job is to verify, contextualize, and decide.

## Nava Labs: The Caseworker Empowerment Toolkit

Nava Labs — the philanthropically-funded research division within Nava PBC — has prototyped and field-tested AI tools with real benefit navigators and caseworkers processing SNAP, Medicaid, WIC, and other public programs. The result is a **Caseworker Empowerment Toolkit**: six purpose-built tools designed around what caseworkers and navigators said they needed.

### The Six Tools

**1. Assistive Chatbot**
An AI-powered chatbot that helps caseworkers answer benefits questions in plain language, grounded in policy documents via RAG. It cites sources directly so caseworkers can verify before using an answer. Designed for rapid-intake settings where a worker may be fielding questions across multiple programs in a single shift.

**2. Form-Filling Assistant**
A generative AI tool that completes benefit application forms with caseworker oversight. The caseworker reviews and approves all filled fields before submission — the AI handles mechanical entry, the caseworker retains responsibility for accuracy.

**3. Referral Generator**
Helps caseworkers connect clients to additional health and social services beyond the primary benefit applied for. Identifies services matched to client characteristics and surfaces referral options the caseworker might not have identified manually. (Early testing found that keyword-based API searches produced unreliable results — this is an area of active development.)

**4. Document Analyzer**
Checks whether client-submitted documents meet program requirements — verifying document type (driver's license, voter registration card), confirming required data fields are present, and flagging missing documentation before submission. Tested with GPT-4o for document type identification and SNAP requirement verification, with positive reception from navigators for the real-time feedback capability.

**5. Call Notes Summarizer**
Transcribes calls and generates structured summaries identifying applicant concerns and next steps. Navigators flagged time-saving as the primary value — writing case notes after every call is a significant administrative burden. Applicants also expressed interest in receiving their own written summary for records.

**6. Work Requirements Checker**
Verifies evidence for benefit programs with work requirements. SNAP and some Medicaid programs require documentation of work activity — this tool validates whether submitted evidence meets the applicable rules.

### The Core Design Constraint

Every tool in the toolkit was built with **human review as a structural requirement**. Navigators vet every AI output before it is used. As the Nava Labs research states directly: "Keep a human in the loop, meaning that navigators will vet a tool's output to ensure accuracy and reduce the risk of harm."

The research also found that organizational support matters as much as tool quality. Sites with active training and peer reinforcement produced "super users" who integrated tools deeply into their workflows. Sites without that support showed weaker adoption regardless of tool quality — a finding with direct implications for how AI rollouts should be planned.

### Call Summarization: Three Techniques Compared

Call note summarization raised the most technically interesting questions. Nava Labs tested three approaches on benefits intake call transcripts:

**Stuffing (full transcript in context)**
Feed the entire transcript to the model at once and request a structured summary. Produced the best results — with Gemini 1.5 and GPT-4/4o — because the Q&A structure of a benefits intake call works well when the model has full context. The model sees the complete conversation when generating the summary. Breaks down when transcripts exceed the model's context window.

**Chunking (segment-and-stitch)**
Break the transcript into segments, summarize each independently, and combine. Scales to any length. But each segment is summarized without context from the rest — details established early in the call may not carry into later segment summaries.

**Refinement (iterative)**
Generate a running summary, updating it after each new chunk. Preserves conversational context across the full transcript length. Requires more model calls than stuffing.

**The finding:** Stuffing with Gemini 1.5 or GPT-4/4o produced the best results for the Q&A transcript format typical of benefits intake calls. The team also developed template requirements specifying essential fields (applicant concerns, next steps, follow-up items) — structured output mattered as much as the summarization technique.
