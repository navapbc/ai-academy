# Deploying Local AI

A chatbot answers questions. An **agent** takes action. This module covers the evolution from simple chat interfaces to autonomous local AI agents — and how Nava can deploy them responsibly in government contexts, where human oversight is non-negotiable.

---

## The Evolution: Chatbot → Grounded Assistant → Agent

### Chatbot
A model that responds to prompts with no external knowledge beyond its training data. Useful for general questions, but has no awareness of your specific documents, databases, or real-time context.

### Grounded Assistant (RAG)
A model augmented with **Retrieval-Augmented Generation (RAG)** — it can search a document store and incorporate relevant passages into its response before answering. Now the model can answer questions about *your* policies, *your* data. Still reactive — it only answers what it is asked.

### Agent
A model that not only answers questions but can **take actions**: search files, query databases, run code, fill out forms, call APIs. It can break a complex goal into subtasks, execute them in sequence, and synthesize results. Agents are the step-change in practical AI capability.

---

## What Makes an Agent Different

The key distinction is **tool use** and **multi-step reasoning**. A chatbot produces text. An agent produces text *and* can invoke external capabilities to gather information or change state in a system.

An agent has:
- A **goal** (what it is trying to accomplish)
- **Tools** (capabilities it can invoke)
- A **reasoning loop** (a structured process for deciding what to do next)
- A **memory** (context from prior steps in the current session)

---

## The ReAct Loop: Reason + Act

The dominant pattern for AI agents is the **ReAct loop**, named for the Reason + Act cycle that drives it. Each iteration has four phases:

**1. Thought**
The model analyzes the current state of the task and decides what information or action is needed to move forward.

**2. Action**
The model invokes a tool — a file search, database query, code execution, API call, or any other defined capability.

**3. Observation**
The model receives and processes the tool's output. This observation becomes input to the next Thought phase.

**4. Repeat or Resolve**
If the task is not yet complete, the loop continues. Once the model has enough information, it produces a final **Answer**.

```
Goal: "Determine if this client is eligible for SNAP based on their intake form."

Thought: I need to check the income threshold for their household size.
Action: policy_lookup("SNAP income limits 2024, household size 3")
Observation: "Gross income limit is 130% FPL = $2,311/month for 3-person household."

Thought: The client's reported income is $1,800/month. I need to verify assets.
Action: policy_lookup("SNAP asset limits, household without elderly member")
Observation: "Asset limit is $2,750 for households without elderly/disabled members."

Thought: Client income and assets are both within limits. I have enough to draft a summary.
Answer: "Based on provided information, client appears eligible. Recommend proceeding to
         full verification. [Draft eligibility summary attached.]"
```

## Tools a Local Agent Can Use

Tools are the capabilities you give an agent. Common tools in govtech contexts:

| Tool | What It Does | Example Use |
|------|-------------|-------------|
| File reader | Reads local documents | Load a claimant's intake form |
| Vector search | Semantic search over a document store | Look up relevant policy sections |
| Code executor | Runs Python/JS snippets | Calculate income ratios, format dates |
| Database query | Queries a local SQLite or Postgres DB | Check prior application history |
| Web search | Searches the public internet | Look up current federal poverty levels |
| Form filler | Populates structured forms | Pre-fill a draft determination letter |

All of these tools can run entirely locally — no external API calls, no data leaving the machine.

---

## MCP: Model Context Protocol

**MCP (Model Context Protocol)** is Anthropic's open standard for connecting AI models to external tools and data sources. Think of it as USB for AI — a standardized plug that lets any model connect to any tool without custom integration code.

MCP defines:
- **Resources**: data sources the model can read (files, databases, APIs)
- **Tools**: actions the model can invoke
- **Prompts**: reusable prompt templates

The key benefit for Nava: MCP-compatible tools built for one AI system can be reused across others. A policy document server built for Claude can also serve a local Ollama model without modification.

## Building a Local RAG Agent with LangChain + Ollama

**LangChain** is a Python framework for building LLM-powered applications. Combined with Ollama, it enables fully local RAG agents with no external dependencies.

### Basic Setup

```python
from langchain_ollama import OllamaLLM, OllamaEmbeddings
from langchain_chroma import Chroma
from langchain.agents import create_react_agent, AgentExecutor
from langchain_community.document_loaders import DirectoryLoader

# Point LangChain at the local Ollama instance
llm = OllamaLLM(model="llama3", base_url="http://localhost:11434")

# Use a local embedding model (no API key needed)
embeddings = OllamaEmbeddings(model="nomic-embed-text")

# Load policy documents and create a vector store
loader = DirectoryLoader("./policy_docs", glob="**/*.pdf")
docs = loader.load()
vectorstore = Chroma.from_documents(docs, embeddings)

# Create a retriever tool
retriever = vectorstore.as_retriever(search_kwargs={"k": 5})
```

### Key Components

- **`nomic-embed-text`**: A local embedding model (pull via `ollama pull nomic-embed-text`) — converts text to vectors without any cloud call
- **ChromaDB**: A lightweight local vector database — stores embeddings on disk, no server setup required
- **`create_react_agent`**: LangChain's built-in ReAct loop — handles Thought/Action/Observation automatically

---

## LlamaIndex: Document-Focused Alternative

**LlamaIndex** is an alternative to LangChain with a stronger focus on document ingestion and retrieval. It excels when your primary use case is Q&A over a large corpus of structured documents — exactly the pattern for policy lookup in govtech.

Choose LangChain for agents with complex tool orchestration. Choose LlamaIndex when the core task is retrieval over many documents.

---

## Privacy Advantages of Local Agents

Running agents locally is not just about compliance — it unlocks capabilities that are impractical in a cloud model:

- **Sensitive file access**: The agent reads private documents (case files, internal databases) without those documents ever leaving the machine
- **No per-call costs**: Agent loops can require 10–50+ LLM calls per complex task. Locally, this is free. At cloud API rates, it becomes expensive fast.
- **Full audit trail on your own infrastructure**: Every tool call, every model input, every output is logged locally — no dependency on a third-party's logging system
- **Air-gap compatible**: Agents can run in fully offline environments — critical for some Nava program contexts

## Govtech Agent Example: Eligibility Pre-Screener

A concrete example of what a local agent looks like in practice at Nava:

**Goal**: Pre-screen a client intake form against eligibility criteria and produce a draft summary for caseworker review.

**Input**: Client intake form (name, household size, income, assets — Tier 3 PII, stays local)

**Tools available to the agent**:
1. `policy_lookup` — semantic search over current program eligibility rules
2. `income_threshold_check` — calculates FPL percentage given income and household size
3. `plain_language_explainer` — rewrites policy language at a 6th-grade reading level

**ReAct loop** (abbreviated):
```
Thought: Check income eligibility first.
Action: income_threshold_check(income=1800, household_size=3, program="SNAP")
Observation: "Income is 78% FPL. Within 130% FPL limit."

Thought: Check categorical eligibility rules.
Action: policy_lookup("SNAP categorical eligibility Oregon 2024")
Observation: "Oregon has broad-based categorical eligibility..."

Answer: [Draft eligibility summary in plain language, flagging items needing verification]
```

**Output**: A structured draft summary the caseworker reviews, edits, and approves — the agent never makes the final determination.

## Production Considerations

Deploying a local agent in a real program context requires more than a working prototype:

| Consideration | What to Address |
|--------------|----------------|
| **Latency** | Multi-step loops can take 30–120 seconds on CPU; set expectations with users |
| **Reliability** | Models occasionally refuse, hallucinate, or loop — build retry and fallback logic |
| **Observability** | Log every tool call and model output; make it easy to audit and debug |
| **Human review gates** | Define clear handoff points where a human must review before action is taken |
| **Model versioning** | Pin the model version; updates can change behavior in unexpected ways |
| **Error handling** | Graceful degradation when a tool fails or returns unexpected output |

## The Non-Negotiable Rule

> **In govtech, agents must always route final decisions through a human caseworker.**

AI agents at Nava are **decision-support tools**, not decision-makers. An agent can:
- Pre-screen and flag likely eligibility
- Draft a determination letter
- Identify missing documentation
- Summarize a complex case history

An agent must **not**:
- Approve or deny a benefits claim without human review
- Send official correspondence to a client
- Update a case record without human confirmation
- Make any determination that affects an individual's access to services

This is not a limitation of current AI capability — it is a fundamental principle of responsible govtech. The caseworker is accountable. The agent is a tool.

## Key Takeaways

- Agents extend models with tools and multi-step reasoning — the chatbot-to-agent evolution is a step-change in practical capability
- The ReAct loop (Thought → Action → Observation → Repeat) is the standard pattern for agent reasoning
- LangChain + Ollama + nomic-embed-text + ChromaDB gives you a fully local RAG agent stack
- MCP provides a standardized protocol for connecting models to tools — reusable across AI systems
- Local agents unlock sensitive-data use cases that are impossible with cloud AI
- The govtech rule is absolute: agents draft, humans decide — no final determination without human review

## Nava in Practice: VA Claims Classification

The U.S. Department of Veterans Affairs processes millions of benefits claims annually. Many of these claims require classifying what type of benefit or service is being requested before they can be routed to the correct processing team — a step that was done entirely manually, creating significant backlog.

Nava worked with the VA to develop an AI classification system that demonstrates what responsible local-first AI looks like in a real federal program context.

### The Challenge

VA claim forms contain free-text descriptions written by veterans and their representatives. Before AI, staff read each submission and manually assigned it to one of dozens of claim type categories. The volume was unsustainable — staff spent significant time on classification work that added no direct value to veterans, while actual case review was delayed.

### The Hybrid Approach

Rather than replacing human judgment entirely, the Nava team designed a **hybrid rule-based and machine learning pipeline**:

1. **Rule-based pre-filter**: A set of deterministic rules handles claims containing clear, unambiguous language — certain form numbers, specific legal citations, explicit benefit names. These require no ML inference and are auditable by any reviewer.

2. **ML classifier for ambiguous cases**: A trained model handles the remaining cases where rule-based logic doesn't apply — free-text descriptions, non-standard language, complex multi-benefit claims.

3. **Confidence thresholding**: Claims below a confidence threshold are routed to human review rather than being auto-classified. The model knows what it doesn't know.

4. **Human review queue**: Borderline and flagged cases go to a human reviewer with the model's top candidate classifications presented as options — the human selects or overrides.

### Results

- Classification accuracy improved from **74% to near 100%** for claim types covered by the hybrid system
- **80% reduction in manual classification work** for in-scope claim types
- Staff time was reallocated from classification to actual case review — work that requires human judgment and directly serves veterans

### What This Teaches Us

Three lessons carry directly to other govtech agent deployments:

**Confidence gating is not a weakness.** A system that routes uncertain cases to humans is more trustworthy than one that always produces an answer. Build explicit handoff points.

**Hybrid rule-based + ML beats pure ML for auditability.** Rules can be read, explained, and contested. When a veteran asks "why was my claim classified as X," a rule-based answer is far easier to explain than a model probability. Reserve ML for the cases where rules genuinely can't cover the variance.

**Measure what matters downstream.** Classification accuracy is a leading indicator, not the outcome. The outcome is: do veterans get their claims processed faster? Nava measured this — not just the model's accuracy, but the reduction in processing time for veterans.
