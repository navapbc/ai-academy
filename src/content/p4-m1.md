# Custom System Prompts

Every interaction with an LLM begins before the user types a single character. The **system prompt** — a block of instructions delivered to the model before any conversation starts — shapes everything that follows: the AI's identity, its knowledge boundaries, its tone, and what it refuses to do. Mastering system prompts is the single highest-leverage skill for anyone deploying AI in a professional context.

> **Key insight:** A mediocre model with an excellent system prompt will outperform an excellent model with no system prompt almost every time. The prompt is the product.

## The "Character Sheet" Metaphor

Think of a system prompt the way a game master thinks of a non-player character's character sheet. Before the game starts, you define:

- **Who they are** — their role, name, and domain expertise
- **What they know** — the background material they can draw on
- **What they must never do** — hard constraints on behavior
- **How they speak** — tone, vocabulary level, response format
- **What they do when confused** — their fallback behavior

The model doesn't improvise those attributes during the conversation — you lock them in before the first user message. This is why system prompts are more powerful than user messages: they establish the ground rules that the rest of the conversation operates within.

## Anatomy of a Strong System Prompt

A production-grade system prompt has five components. Each one is load-bearing.

### 1. Identity

Tell the model exactly who it is — its role, organization, and area of expertise. Be specific. "Be helpful" is not an identity. "You are a policy analyst at a civic technology firm specializing in Medicaid eligibility rules for the state of Colorado" is an identity.

```
You are a benefits eligibility assistant working on behalf of Nava.
You specialize in SNAP, Medicaid, and CHIP eligibility rules.
```

### 2. Context

Describe what the model should know and reference. This is where you anchor it to specific documents, time periods, or datasets. If you're using RAG, this section tells the model how to treat the retrieved material.

```
You have been provided with the current Colorado Medicaid eligibility manual
(effective January 2025). Use this document as your primary source.
```

### 3. Constraints

List what the model must never do. Use explicit negative language. This is where you prevent hallucination, scope creep, and off-brand responses. The **negative constraint pattern** — "Never X unless Y" — is one of the most effective tools in prompt engineering.

```
Never speculate about eligibility outcomes beyond what the provided document states.
Never quote specific dollar thresholds unless those exact figures appear in the context.
Never provide legal advice. If a user asks for legal guidance, direct them to a licensed attorney.
```

### 4. Output Format

Specify exactly how the model should structure its response. Unformatted prose forces readers to extract the answer themselves. Defined formats reduce cognitive load and improve accessibility.

```
Respond in plain language at an 8th-grade reading level.
Use numbered lists for multi-step processes.
Use a single bolded sentence to state the key finding before elaborating.
Keep responses under 250 words unless detail is explicitly requested.
```

### 5. Edge Cases

Tell the model what to do when it hits the edges of its knowledge or the user's question falls outside scope. Without explicit instructions, models speculate. With them, they surface uncertainty clearly.

```
If the answer is not contained in the provided context, say exactly:
"I don't have enough information in the current document to answer that.
You can contact the Benefits Help Line at [number]."
Do not attempt to answer from general knowledge.
```

## The Five Nava AI Personas

Nava has defined five reusable AI personas for common project contexts. Each is a pre-written system prompt foundation that team members can customize for their specific use case.

| Persona | Core Role | Primary Constraint |
|---|---|---|
| **Policy Analyst** | Synthesize regulatory text, identify gaps, flag changes | Never speculate beyond cited source material |
| **Empathy Auditor** | Review citizen-facing copy for fear-inducing or exclusionary language | Maintain legal accuracy while rewriting |
| **Technical Writer** | Convert engineering specs into plain-language documentation | Target 8th-grade reading level, active voice only |
| **Standard Assistant** | General-purpose task support | Stay within the project's data handling boundaries |
| **Custom Persona** | Team-defined for a specific project need | Documented in the project repo |

## Worked Examples

### Benefits Eligibility Assistant

```
You are a benefits eligibility assistant for Nava deployed on a state
Integrated Eligibility System. Your role is to help caseworkers quickly
identify which programs a household may qualify for based on the household
characteristics the caseworker describes.

You have been provided with the current state eligibility rulebook as CONTEXT.
Use ONLY this document. Do not reference federal policy unless it is explicitly
cited in the provided state document.

For each program, respond with:
1. Program name
2. Likely eligible / Likely ineligible / Insufficient information
3. The specific rule from the context that drives that determination
4. Any missing information the caseworker should collect

If you cannot determine eligibility from the provided context, say:
"The provided rulebook does not cover this scenario. Please escalate to a
policy specialist."

Never tell a caseworker that an applicant is definitively eligible or
ineligible — only that they appear likely to qualify or not based on the
information available. Final determination is always made by the system.
```

### Accessibility Auditor

```
You are an accessibility auditor at Nava specializing in WCAG 2.1
compliance and plain-language standards for government digital services.

When given a document or UI copy, you will:
1. Flag any language that may be confusing for users with low literacy,
   cognitive disabilities, or limited English proficiency.
2. Identify passive voice constructions and suggest active alternatives.
3. Check that error messages explain what went wrong AND what to do next.
4. Note any technical jargon that lacks a plain-language equivalent nearby.

Format your response as a table with columns:
| Issue | Original text | Suggested revision | WCAG criterion |

Do not rewrite the entire document. Flag issues and propose targeted fixes.
If a passage has no accessibility concerns, say "No issues found in this section."
```

### Document Summarizer

```
You are a policy document summarizer at Nava.

Your task: given a policy document in CONTEXT, produce a structured summary
for a senior program manager who has 3 minutes to read.

Output format:
**What changed:** [1-2 sentences]
**Who is affected:** [specific populations or programs]
**Effective date:** [exact date from document]
**Action required:** [what the team must do before effective date]
**Open questions:** [anything the document leaves ambiguous]

Use exact language from the document for dates, thresholds, and proper nouns.
Do not interpret ambiguous language — surface it as an open question instead.
Maximum 200 words.
```

## Common Mistakes

**Too vague.** "Be helpful and professional" gives the model no meaningful constraints. Every model already tries to be helpful. You must specify what "helpful" means in your exact context.

**Too long.** System prompts beyond 1,500 tokens begin to suffer from **middle-of-prompt forgetting** — the model gives less attention to constraints buried in the middle. If your prompt exceeds one screen, restructure it. Put the most critical constraints first and last.

**No output constraints.** Without format instructions, the model decides its own structure. In production, inconsistent output format breaks downstream parsing and creates review overhead.

**Missing fallback instruction.** If you don't tell the model what to do when it doesn't know, it will guess. In govtech contexts, a confident wrong answer is worse than an admitted knowledge gap.

**No negative constraints.** Positive instructions ("be accurate") are weaker than negative ones ("never state a dollar amount that does not appear in the provided document"). Be explicit about the failure modes you're preventing.

## Treating Prompts Like Code

System prompts are software. They have versions, they can introduce regressions, and they need tests.

**Version control:** Store system prompts in your project's git repository. Every change should be a commit with a message explaining what changed and why. Never edit a production prompt in a chat interface.

**Changelog:** Keep a short log of prompt versions. When an AI output changes unexpectedly, the first question is "did the prompt change?"

**Test suite:** Define a set of test inputs with expected outputs before deploying. Include at least three edge cases — queries the prompt should refuse or redirect. Run these against any new version before promoting it.

**Review:** The Nava standard for AI-assisted deliverables requires that the system prompt used to generate any citizen-facing output is documented and human-reviewed before publication. The prompt is part of the deliverable, not a behind-the-scenes detail.

> **The Nava rule:** Every AI-assisted deliverable must have a visible system prompt on record and must pass a human review before it reaches a caseworker, applicant, or government partner.
