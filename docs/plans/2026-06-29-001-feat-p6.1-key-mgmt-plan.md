# P6.1 — Key Management + (light) Provider Seam Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rotate the live Anthropic key off a personal/dev token onto the Nava org token, centralize the duplicated model/provider config behind a light Claude-only seam, close the `grade` function's missing model-allow-list check, and document key rotation as an operational runbook.

**Architecture:** The `ANTHROPIC_API_KEY` already lives only in the Deno runtime of two Edge Functions (`chat`, `grade`) and never reaches the browser — that isolation is done. P6.1 is the *remaining* hardening: (1) an ops rotation of the live key, (2) a small refactor that makes the model id / API endpoint / wire version a single source of truth per function with an additive `provider` field (so a second provider *could* slot in later — no adapter built now, per decision D1), and (3) validating the operator-configured default model against the allow-list in both functions. No new providers, no dated-snapshot model pinning (LLM-10 stays accepted-as-deferred).

**Tech Stack:** TypeScript (strict), Deno (Edge Functions), Vitest (pure-logic tests), Supabase CLI + GitHub Actions (`deploy.yml`) for deployment.

## Global Constraints

- **Branch:** `feat/p6.1-key-mgmt` (already created off `main`). Never commit to `main`.
- **Node 22** for all `npm` commands (jsdom tests throw `ERR_REQUIRE_ESM` on Node 20) — `nvm use 22` first.
- **Strict TypeScript:** zero `any` / `@ts-ignore` in production source. `tsconfig.json` **excludes `supabase/`** (Edge Functions are Deno) — do not import a `supabase/` file from `src/` production code.
- **Deno independent bundling:** the deployed `grade` function must **not** cross-import from `chat/`. Config is duplicated between `chat-core.ts` and `grade/verdict.ts`; a vitest parity test (which runs under node, not the deployed bundle) keeps them in sync.
- **Decisions locked:** Claude-only (light seam, no OpenAI/Google adapter); model pinning stays deferred.
- **Do not alter the grade judge's behavior:** `GRADE_SYSTEM_PROMPT`, `buildGradeUserMessage`, and `parseVerdict` are unchanged — the judge stays byte-equivalent. P6.1 only touches model/endpoint config and the env-default validation.
- **Deploy path:** merge to `main` auto-deploys to **staging**; the `release` branch deploys to **prod**. Edge Functions deploy via the pipeline (`supabase functions deploy`); the API key is set out-of-band with `supabase secrets set` on the Supabase project, **not** as a GitHub secret.
- **Commits:** conventional, scoped to `p6.1`, referencing audit ids where relevant (`D-23`, `LLM-10`). Commit messages end with the `Co-Authored-By` trailer.

The pipeline targets a `staging` project and (via the `release` branch) a `production` project. Get each `<ref>` from GitHub → Settings → Environments → (each env) → the `SUPABASE_PROJECT_REF` secret, or from the project URL `https://<ref>.supabase.co`.



- [ ] **Step 4: Verify the new key works before revoking the old one**

In each deployed environment, sign in as a `@navapbc.com` user and exercise one chat stream (the Playground) and one graded lab. Both should succeed. (No redeploy needed — the new secret is read on the next call.)

- [ ] **Step 5: Revoke the old personal/dev key in the Anthropic console**

Only after Step 4 passes in **prod**. Confirm chat/grade still work after revocation (proves nothing else depends on the old key).

- [ ] **Step 6: Verify `APP_ORIGIN` is set for cross-origin CORS**

Both functions' CORS allow-list only admits the prod site when `APP_ORIGIN` is set on the Supabase project (else they silently fall back to localhost-only origins and prod browser calls are CORS-blocked).
```bash
supabase secrets list --project-ref <prod-ref>   # confirm APP_ORIGIN present
```
If absent, set it to the deployed site origin (scheme + host, no trailing slash), e.g.:
```bash
supabase secrets set APP_ORIGIN=https://<your-prod-site> --project-ref <prod-ref>
supabase secrets set APP_ORIGIN=https://<your-staging-site> --project-ref <staging-ref>
```
Record the resolved values — they feed Task 4's secrets inventory.

```ts
// --- Provider + model config (SEC-03 / LLM-03 / P6.1) -----------------------
// Single source of truth for this function. The server is authoritative: a raw
// request naming any other model is rejected, so a caller can't force an
// expensive model regardless of the UI. `provider` is the deliberate light seam
// (P6.1, D1) — Claude-only today; a second provider would be an *additive*
// entry here, not a built-out abstraction. Mirrored (not imported) in
// grade/verdict.ts so each function bundles independently under Deno; a vitest
// parity test keeps the two in sync.
export interface ModelDescriptor {
  id: string;
  provider: 'anthropic';
}

export const MODELS: ModelDescriptor[] = [
  { id: 'claude-haiku-4-5', provider: 'anthropic' },
  { id: 'claude-sonnet-4-6', provider: 'anthropic' },
];

export const MODEL_ALLOWLIST: string[] = MODELS.map((m) => m.id);

// The safe hardcoded fallback used when no (or an invalid) ANTHROPIC_MODEL env
// is configured — must itself be allow-listed.
export const FALLBACK_MODEL = 'claude-haiku-4-5';

// Anthropic Messages API endpoint + pinned wire version (was inlined in index.ts).
export const ANTHROPIC_API = {
  url: 'https://api.anthropic.com/v1/messages',
  version: '2023-06-01',
} as const;

export function isModelAllowed(model: string): boolean {
  return MODEL_ALLOWLIST.includes(model);
}

/**
 * Resolves the operator-configured default model: the env value if it's on the
 * allow-list, else the safe fallback. Stops a typo'd ANTHROPIC_MODEL from
 * sending an off-list/invalid model on requests that omit `model` (P6.1).
 */
export function resolveDefaultModel(envModel: string | undefined): string {
  return envModel && isModelAllowed(envModel) ? envModel : FALLBACK_MODEL;
}
```
