# P6.2 — Claude Usage Tracking + Admin Monitoring

## Problem Frame

All Claude calls route through the `chat` and `grade` Supabase Edge Functions, but the app has **no durable record of usage** — only a per-isolate in-memory rate limit (`fixedWindowAllow`, D-21). Admins can't see who is consuming API budget, and a runaway bug or abusive pattern could burn spend unnoticed. This is Phase 6 hardening for an internal app with modest projected spend (~$1–3k total), so the goal is **visibility + early warning**, not aggressive gating.

## Decisions (resolved in brainstorm)

- **Enforcement = monitor + alert only.** Usage is tracked and surfaced to admins, with threshold alerts, but **model calls are never blocked** on a usage cap (avoids interrupting a learner mid-lab).
- **Dimension = per-user.** Track and attribute usage per learner (cohort rollup is a nice-to-have view, not an enforced budget).
- **Accounting = token counts only.** Persist input/output token counts + call counts per model; **no dollar conversion** (no price table to maintain).
- **Cheap default already shipped.** Haiku is the default/fallback model (`chat-core.ts FALLBACK_MODEL`) — no work needed.

## Requirements

**Usage capture**
- R1. On every Claude call via the `chat` and `grade` Edge Functions, durably record: `user_id`, source (`chat` | `grade`), model, input tokens, output tokens, and timestamp.
- R2. Token counts come from the Anthropic API response usage (not estimated); a failed/partial call records what's available (or is skipped) without breaking the user-facing call.

**Admin visibility**
- R3. An **admin-only** usage view (in the existing staff area) showing per-user totals (calls, input/output tokens) over a selectable window, sortable to surface the heaviest consumers, with a cohort rollup for context.
- R4. **Threshold alerts (monitor-only):** when a user crosses a configurable per-window token/call threshold, flag it in the admin view (and log it). No learner-facing effect, no blocking.

**Boundaries**
- R5. Usage tracking must **never deny or degrade** a model call; the existing rate limit remains the only limiter.

## Success Criteria
- An admin can see which learners consume the most tokens/calls over a window and is flagged on outliers.
- Usage is **durable** (survives Edge Function isolate restarts) — unlike the current in-memory counter.
- **Zero learner-facing behavior change.**

## Scope Boundaries
- No dollar/cost estimation (token counts only).
- No hard or soft caps; no blocking of any call.
- No per-cohort enforced budget (cohort view is read-only rollup).
- No learner-facing usage UI.
- Not fixing the in-memory rate-limit durability (D-21) — adjacent; the new usage table could later back a durable limiter, but that's out of scope here.

## Key Decisions
- Monitor-only over enforcement: proportional to an internal, low-spend app; protects learner UX.
- Token counts over $: avoids maintaining a per-model price table; raw tokens still rank consumers and catch runaways.
- Reuse the staff-area/admin pattern (`src/lib/dashboard.ts` + `is_admin()` reads) rather than a new surface.
