# P4.4a — "Synthesis" Lab (cell 2.7)

**Phase:** P4.4a — *A graded "minority-voice synthesis" exercise on cell 2.7, scored by the existing P4.2 LLM-judge against a rubric, shown in place. Practice, not a gate.*
**Depends on:** P4.3b (#48 — the `{brief, sections[]}` grade judge, `requestLlmGrade`/`saveGrade`/`recordLabSubmission`, and the shared `GradeResultCard`), P3.6/P3.7 (the render-above-the-quiz exercise pattern).
**Date:** 2026-06-03
**Branch:** `feat/p4.4a-synthesis-lab`

## 1. Goal

Add a new interactive exercise — **Synthesis** — where the learner reads a set of source
excerpts (synthetic user-interview notes) in which most participants agree but one or two
dissent, and writes a synthesis that **preserves the minority view** instead of flattening it
into a tidy false consensus. The synthesis is graded by the **existing P4.2 LLM-judge** (`grade`
Edge Function) against an anchor rubric, and the anchor-scored result renders in place (reusing
P4.2/#48's `GradeResultCard`).

This is **graded practice that records a `lab_submission` but does NOT gate completion**. Cell
2.7 is `type:'content'` with an inline quiz; the **quiz stays the completion gate** (same pattern
as the P3.6/P3.7 exercises and the #48 critique — render above the quiz, never call
`onComplete`).

Wired on one cell:
- **2.7 "AI for synthesis"** — synthesize ten interview notes about a new online
  unemployment-insurance (UI) claim flow. Most claimants found it fast and clear; two could not
  (one could not finish on library wi-fi before the session timed out; one gig/1099 worker had no
  way to enter self-employment income). A good synthesis keeps those two voices.

**Out of scope:** champion-review UI/RLS (P5.1, unchanged); retrofitting other exercises; the
judge's prompt/parser (`GRADE_SYSTEM_PROMPT`, `parseVerdict` — untouched); any change to the
`chat` function or the quiz gate. No regression to the 2.1 lab or the 2.2/2.3 critique behavior
introduced in #48.

## 2. Context (current state, post-#48)

- **The P4.2 judge** (`supabase/functions/grade/{verdict.ts,index.ts}`) is non-streaming,
  hardened, and — as generalized in #48 — takes `GradeSubmission = { brief: string; sections:
  { label; text }[] }`. `buildGradeUserMessage(rubric, submission)` renders the brief then each
  `LABEL:`\n`text` verbatim. This already fits a synthesis with no judge change at all: we pass
  `sections: [{ label:'Source excerpts', text: sources.bodyMd }, { label:"The learner's
  synthesis", text }]`.
- **The client grading path** (`src/lib/grading.ts requestLlmGrade`, `src/lib/progress.ts
  recordLabSubmission`→id + `saveGrade`) is reusable as-is.
- **`src/components/GradeResultCard.tsx`** (extracted in #48) is the anchor-scored card
  (`#grade-result`, "Anchor-scored feedback … Provisional — pending review", per-anchor list).
  Reused as-is, no edit.
- **`src/components/exercises/Critique.tsx`** (#48) is the exact template: render a sourced
  markdown block (`ReactMarkdown + remarkGfm`) + a brief + a min-words-gated textarea; Save →
  `recordLabSubmission({transcript:{kind,…},status:'submitted'})` → `requestLlmGrade({rubric,
  submission})` → `saveGrade(id, result, 'reviewable')` → `<GradeResultCard>`. No `onComplete`.
  Critique and Synthesis are **~90% identical** (brief + one sourced markdown block + a free-text
  textarea + the same judge/result flow); the only differences are copy, the source-section
  label, the transcript discriminant, and the icon.
- **The exercise dispatch:** `ModuleRenderer.renderExercise()` switches on
  `module.labConfig.kind`; the inline quiz renders after and gates. Structural "not a gate"
  guard: the component's `Props` are `{ config, labId }` only — a `@ts-expect-error` test asserts
  `onComplete` is not accepted (see `exercises.test.tsx` for OutputAudit/Calibration).
- **Content lives in two places:** lesson/quiz come from `curriculum-content.json` (already
  seeded for 2.7 — "AI for synthesis", 3 quiz questions). **Lab configs come from migrations.**
  Cell 2.7 has body+quiz but **no `lab_config_json`** yet.
- **The 2.7 lesson's worked example** is twelve interviews about a *benefits portal* where a
  *screen-reader* user's failure vanished into a "clarity" theme. Reusing that would hand the
  learner the answer — so the exercise uses a **different** scenario (UI claim flow) and
  **different** minority voices (a low-connectivity claimant + a gig/1099 worker).

## 4. The shared component (D3) — byte-stable Critique is the hard constraint

New `src/components/exercises/SourcedFreeTextLab.tsx` — generic, props-driven. It owns the
entire flow that Critique has today: header, one sourced markdown block, the brief, the
min-words-gated textarea + live counter, Save → record → grade → `GradeResultCard`, the
grading/`aria-live` status, the saved-state read-back, and the quiet grading-failure note.

```ts
interface SourcedFreeTextLabProps {
  labId: string;
  /** Transcript discriminant; also derives the response section label + all "your <noun>" copy. */
  noun: 'critique' | 'synthesis';
  containerId: string;                       // the wrapper's #id ('critique' | 'synthesis')
  icon: ReactNode;
  title: string;                             // already-resolved (wrapper applies its own default)
  subtitle: string;
  source: { label: string; bodyMd: string }; // the markdown block under the brief
  sourceSectionLabel: string;                // grade section label ('Artifact under review' | 'Source excerpts')
  brief: { instruction: string };
  rubric: GradingRubric;
  textareaPlaceholder: string;
  minWords: number;
}
```

**How `noun` keeps Critique byte-identical.** Everything Critique's tests/markup assert is
derived from `noun='critique'`:
- textarea `aria-label` = `Your ${noun}` → `"Your critique"`;
- Save button = `Save ${noun}` → `"Save critique"`;
- transcript = `{ kind: noun, [noun]: text.trim(), wordCount }` → `{ kind:'critique', critique,
  wordCount }` (**byte-identical** to #48);
- grade response section label = `The learner's ${noun}` → `"The learner's critique"`;
- not-signed-in error = `Sign in to save your ${noun} — it's graded below.`;
- grading-failure note = `Grading is unavailable right now — your ${noun} is saved.`;
- grading status = `Grading your ${noun}…`.

`Critique.tsx` becomes a thin wrapper that maps `CritiqueConfig` → these props (icon `ScanSearch`,
its existing title/subtitle defaults, `source = config.artifact`, `sourceSectionLabel='Artifact
under review'`, `containerId='critique'`, `noun='critique'`, `minWords=40`, its existing
placeholder). **`Critique.test.tsx` is left unchanged and must stay green** — that is the proof of
byte-stability (renders the artifact, word-floor gate, `recordLabSubmission` kind:'critique',
`requestLlmGrade` with sections `Artifact under review` + `The learner's critique`,
`saveGrade('sub-1', …, 'reviewable')`, the `/grading is unavailable/i` note).

`Synthesis.tsx` is the sibling wrapper that maps `SynthesisConfig` → these props (icon `Layers`,
its own defaults, `source = config.sources`, `sourceSectionLabel='Source excerpts'`,
`containerId='synthesis'`, `noun='synthesis'`, `minWords=50`).

> **Rejected alternative:** copy Critique into a standalone `Synthesis.tsx` (~180 lines of
> duplication). Lower regression risk but rots two near-identical components; the team's
> `GradeResultCard` extraction shows the DRY bar. Mitigation for the chosen path: Critique's
> tests are the regression net and stay byte-stable.

## 6. Content — the source set, rubric, and the ANSWER KEY (synthetic)

> Authoring bar (`docs/content-guide.md`): no AI-isms; realistic civic-tech context. This is
> **synthetic** research data (authored interview notes) — there is no external-fact risk — but
> the notes are internally consistent and the minority/dissenting voices are genuinely present in
> the source so the rubric is fair. The scenario (an online UI-claim flow) and the minority-voice
> types (low connectivity; gig/1099 income) intentionally **differ** from the 2.7 lesson's worked
> example (a benefits portal where a screen-reader user's failure was lost to a "clarity" theme),
> so the exercise doesn't hand the learner the answer.

**Research question (in the source):** How did claimants experience filing an *initial*
unemployment-insurance claim through the new online portal (which replaced the phone-only
intake)?

**Brief (instruction):** "A researcher gave you these notes from ten interviews about the new
online unemployment-claim flow, and a readout is due tomorrow. Synthesize them into the themes
you'd present — but don't let the tidy summary drop the voice that should change the design.
Cover the themes, how widely each was felt, and what still needs follow-up."

**Source excerpts (markdown, 10 short notes):** see the migration body. Shape:
- **Majority (8/10), broadly positive** — faster than the old phone line (P1), a reassuring
  progress bar (P2), plain-language "base period" (P3, *marked as the researcher's paraphrase*),
  "straightforward" on a home laptop (P4), save-and-return (P5), a confirmation/claim number that
  lowered anxiety (P6), plus two with **minor gripes** (P8: SSN field doesn't auto-format; P10:
  wished for a phone number).
- **Minority (2/10), materially important** — **P7**: no home internet/computer, filed from her
  phone on the public library's wi-fi; the session timed out after ~20 min of inactivity while
  she looked up a former employer's address, cleared her entries, and the library closed before
  she could finish — **she left without a submitted claim**. **P9**: drives for two delivery apps
  (1099); the employer section required an employer name + a state UI account number with **no
  self-employment / independent-contractor option**, so he guessed and **isn't confident his
  claim is accurate**.
- **Fidelity traps planted on purpose:** (i) P3's note is explicitly the *researcher's
  paraphrase*, so rendering it as a verbatim participant quote is fabrication; (ii) there is **no
  satisfaction statistic** in the source, so any "% satisfied" figure is invented; (iii) the
  timeout is specific to P7's library-wi-fi context, so generalizing "the session times out for
  everyone" misreads the source; (iv) 8/10 positive tempts an over-generalized "everyone/all
  users loved it."

**Rubric anchors (4 × 0–2):**

| id | label | description (what a good synthesis does) |
|----|-------|------------------------------------------|
| `surface-minority-voice` | Surface the dissenting voice | Surfaces the minority reactions that materially matter — the claimant who couldn't finish on library wi-fi before the session timed out (no home internet/device) and the gig/1099 worker with no way to enter self-employment income — rather than presenting a false consensus that the flow works for everyone. |
| `honest-weighting` | Weight the views honestly | Represents how many felt what without distortion: most participants (about 8 of 10) completed quickly and positively, while one could not finish and one is unsure the claim is accurate — neither overstating the positive ("everyone/all") nor inflating the minority. |
| `source-fidelity` | Stay faithful to the source | No fabricated or misattributed quotes (e.g. does not turn the researcher's paraphrase into a verbatim participant quote) and no invented statistics; attributes the timeout to the specific library-wi-fi context rather than generalizing it to all users. |
| `flag-follow-up` | Flag the gaps | Flags what needs follow-up or where the sample is thin — a small single-channel sample of ten skews toward people with devices/connectivity who completed the flow, and the gig-income path and the low-connectivity/timeout experience need dedicated research. |

**ANSWER KEY — what a good synthesis MUST preserve:**

1. **The two minority voices are kept, not averaged away.** P7 (could not complete — library
   wi-fi + ~20-min session timeout, no home internet/device) and P9 (gig/1099 worker, no
   self-employment income option, uncertain accuracy) are surfaced as findings that should change
   the design, **not** folded into a "mostly positive" theme. Missing both → anchor
   `surface-minority-voice` = 0.
2. **Weighting is honest.** ~8 of 10 were positive and finished; exactly **one** could not finish
   and **one** is unsure of accuracy. A good synthesis neither says "all/everyone loved it" nor
   implies "many couldn't finish." It notes the sample is small.
3. **Fidelity is preserved.** No invented satisfaction statistic; P3's paraphrase is not promoted
   to a verbatim quote; the timeout is attributed to P7's library-wi-fi context, not generalized.
4. **Gaps are flagged.** The sample (n=10, one recruiting channel) skews toward people who had
   devices/connectivity and completed the flow (survivorship); the 1099-income path and the
   low-connectivity/timeout experience are called out for dedicated follow-up.

**Framing grounded in the lesson's own sources** (no new external claims introduced): synthesis
"saves the most time of any use case, and it also causes the most subtle harm"; a flattened
summary "can quietly erase the accessibility complaint or the minority experience that should
have changed the design." (Lesson 2.7 "AI for synthesis"; CDT, *Generating Confusion* (Sept
2024); Anthropic AI Fluency Index (Feb 2026).)
