# P4.9 — Personal failure-mode log (cell 2.9)

**Item:** Phase 4 P4.9 (remediation W4-2) — the portfolio instrument for cell 2.9. Additive: a new
`LabConfig` kind + component + pure gate + dispatch + seed. Mirrors P4.8's capture pattern.
**Date:** 2026-06-09
**Branch:** `feat/p4.9-failure-log`

## What 2.9 is (from the loaded lesson, migration `20260602190000`)
"Recognizing AI failure modes specific to your work." A **personal failure-mode log** is the
learner's own dated record of the specific ways AI breaks on the work they actually do. The lesson
says: when AI burns you, log **the task, the exact error, how you caught it, and the tell that gave
it away**; group repeats into patterns; read the matching entries before a similar task. DoD: a
**dated failure-log portfolio, ≥6 entries over time**. `evidenceType='portfolio'`.

## Instrument (additive, same family as P4.8 `UseCasePortfolio` / `ReflectionCapture`)
A new `failure-log` lab kind. Cell 2.9 is a `content` module with an inline quiz (the completion
gate), so this is graded PRACTICE that records a `lab_submissions` row and **never calls
onComplete** — enforced by the component taking only `{config, labId}`. It is a captured exit
artifact (**not LLM-graded**), behind a completeness gate.

Each log entry has a **date** plus four fields the lesson names: **task**, **what went wrong** (the
exact error), **how you caught it**, and the **tell** (the signal to watch next time). Add/remove
entries; an entry counts as complete only when date + all four fields carry text.

**"≥6 over time" → a shown target with a modest record floor.** Cross-session accumulation is a P5
follow-up (entries are built in-session and snapshotted into the submission), and requiring six
complete entries in one sitting contradicts the lesson's "build it over time" framing. So the config
carries a hard `minEntries` floor (default **3** — enough to record meaningful practice) and a soft
`targetEntries` (**6**, the portfolio goal) shown in the counter and encouraged in copy — the same
soft-target/hard-floor split used by `ReflectionCapture` (words) and `UseCasePortfolio`.

On submit: `recordLabSubmission(user.id, { labId, transcript: { kind:'failure-log', entries,
entryCount }, status:'submitted' })`, then a saved confirmation. A `role="status"` readiness line
lists what's still needed.

## Pure core (testable): `failureLog.ready.ts`
`evaluateFailureLogReadiness(entries, config) -> { ready, reasons[], completeEntries }` — complete
entries ≥ `minEntries`. Returns reasons for the readiness line and gates Submit.

## Config (content-as-data) — `FailureLogConfig`
`intro`, the section `title`/`helper`, `minEntries`, `targetEntries`, and the field placeholders
(task / error / caught / tell). Seeded for 2.9 via an idempotent
`update … where cell_id='2.9' and lab_config_json is null` migration at `status='in_review'`
(body_md/quiz_json untouched — the lesson + quiz gate stay intact).

## Out of scope
Cross-session accumulation / read-back (P5 follow-up), LLM grading, any completion-semantics change,
P4.10. No shared "portfolio base" abstraction with P4.8 — the two instruments differ enough (dated
4-field entries vs. helps/doesn't entries + a 4D statement) that the codebase's per-instrument
convention is clearer than a premature shared component.
