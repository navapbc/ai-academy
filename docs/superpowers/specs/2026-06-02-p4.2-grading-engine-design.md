# P4.2 — Grading Engine

**Phase:** P4.2 — *Auto (keys) + LLM-as-judge via Claude (anchor-scored, labeled reviewable) + champion-review.*
**Depends on:** P4.1 (the generalized `Lab`), P1.2 (the Claude Edge Function proxy).
**Date:** 2026-06-02
**Branch:** `feat/p4.2-grading-engine`

## 1. Goal

Build the grading engine that scores lab work two ways and records the result in
a uniform shape:

- **LLM-as-judge** — a new server-side `grade` Edge Function calls Claude to
  anchor-score a free-text lab submission against a rubric, returns a structured
  JSON verdict, and the result is stored on the submission and **labeled
  `status='reviewable'`** (provisional, pending human review).
- **Auto (keys)** — a pure, deterministic grader producing the *same* result
  shape for keyed labs.

Demonstrated end-to-end on cell **2.1** (the only existing lab): add an anchor
rubric to its config, grade its submission via the judge, show the learner an
anchor-scored result.

**Out of scope (deferred to P5.1):** the champion-review UI and the champion RLS
policies that let a champion read/grade *other* learners' submissions. P4.2 only
produces the `reviewable`-labeled, anchor-scored artifacts that surface will
consume. Also out of scope: retrofitting the existing client-graded exercises
(classifier, sorter, etc.) through the new engine.

## 2. Context (current state)

- **`lab_submissions`** already has the grading columns (from the P1.1 init
  migration): `transcript jsonb`, `rubric_scores jsonb`, `grader text`,
  `status text`. RLS is **owner-only** with select/insert/**update** policies, so
  a learner can update their own submission row. Champion/admin policies are
  explicitly deferred to P5.1.
- **`profiles.role`** already allows `'champion'` / `'admin'`, but no champion
  RLS exists yet — so champions cannot read others' submissions today.
- **The `chat` Edge Function** (`supabase/functions/chat/index.ts`) holds the
  Anthropic key server-side and **streams text** deltas; it's hardened (JWT
  authz, CORS, model allow-list, `max_tokens` clamp, upstream errors logged not
  forwarded). `src/lib/llm.ts` calls it with `fetch` + a stream reader. Grading
  needs a **non-streaming, structured-JSON** contract, so it gets its own function.
- **The `Lab` component** (`src/components/Lab.tsx`, from P4.1) is the
  prompt-construction lab: it runs the learner's prompt against Claude and, on
  **Save & complete**, calls `recordLabSubmission(user.id, { labId, transcript, status })`
  (inserts a row) and `onComplete()`. `recordLabSubmission` currently returns `void`.
- **`mastery_anchor`/`emergent_anchor`** columns on `modules` exist but are
  unpopulated; per-lab grading rubrics are authored as content, so P4.2 carries
  the rubric on the lab's `lab_config_json` (content-as-data) rather than those
  columns.

## 3. Decisions

| # | Decision | Choice |
|---|----------|--------|
| D1 | Scope vs champion-review | **Engine core only.** Label LLM grades `status='reviewable'`; the champion-review UI + RLS are P5.1. |
| D2 | LLM-judge mechanism | **New `grade` Edge Function** (server-side, non-streaming, returns structured JSON). |
| D3 | Demonstrable slice + auto-keys | **Wire the LLM judge end-to-end on cell 2.1**; ship a pure, unit-tested `autoGrade` (same result shape) for future keyed labs, **not wired** to any cell; do not retrofit existing exercises. |
| D4 | Grading flow | **Save → grade → Continue** (revised after in-app verification). For a lab WITH a rubric, the primary button inserts the submission (`submitted`) and grades it *in place* — it does NOT auto-advance, because `onComplete` advances the cursor and would unmount the lab before the grade renders. The grade card (or a "grading unavailable" note) then shows a **Continue** button that calls `onComplete` to advance. Completion never blocks on grading (Continue appears even if grading fails). A lab WITHOUT a rubric keeps the original one-click save-and-complete. |
| D5 | Rubric source | The lab's `lab_config_json.rubric` (content-as-data), seeded for 2.1. Drafted for SME review (`status='in_review'`). |
| D6 | Result shape | A unified `GradeResult` (per-anchor 0–2 + rationale, overall sum) stored in `rubric_scores`, with `grader` ∈ {`llm`,`auto`}. |

## 4. Verdict shape & the `grade` Edge Function (§1)

**Unified result shape** (TS in `src/lib/grading.ts`; the JSON the function
returns; stored in `lab_submissions.rubric_scores`):

```ts
export interface AnchorScore { id: string; label: string; score: number; max: number; rationale: string }
export interface GradeResult {
  grader: 'llm' | 'auto';
  perAnchor: AnchorScore[];
  overall: number;     // sum of anchor scores
  maxOverall: number;  // sum of anchor maxes (each anchor max = 2)
}
```

**`supabase/functions/grade/index.ts`** — second server-side function holding the
Anthropic key, reusing the `chat` hardening (JWT authz, CORS, model allow-list,
token clamp; upstream errors logged not forwarded). **Non-streaming JSON** contract:

- **Input:** `{ rubric: { anchors: { id; label; description }[] }, submission: { brief; prompt; response } }`.
- Calls Claude `/v1/messages` (non-streaming) with a grading **system prompt**
  instructing it to score each anchor **0–2** (0 not-met, 1 partial, 2 met)
  against its `description` and return **strict JSON** matching `perAnchor`
  (`{ id, score, rationale }` per anchor). Low temperature for consistency.
- **Parse + validate** the model's JSON via a pure helper (see §4 testing): every
  rubric anchor present exactly once, each `score` an integer in 0–2. On
  malformed output → return an error (HTTP 502-style JSON `{ error }`); the
  client then leaves the submission ungraded rather than storing a fabricated
  score. On success, compute `overall`/`maxOverall` and return
  `{ perAnchor, overall, maxOverall }` (the client stamps `grader:'llm'`).

## 5. Rubric data + client flow (§2)

**Rubric on the config (content-as-data).** In `src/types.ts`:

```ts
export interface GradingRubric { anchors: { id: string; label: string; description: string }[] }
// added (optional) to PromptConstructionConfig:
rubric?: GradingRubric;
```

A migration seeds cell 2.1's `lab_config_json.rubric` with four anchors (drafted,
`status='in_review'`): `role-context`, `constraints-up-front`,
`definition-of-done`, `output-meets-brief` — each with a `description` the judge
scores against.

**Client data-access:**
- `src/lib/grading.ts` — `requestLlmGrade({ rubric, submission })`: `fetch`es the
  `grade` function with the session access token (mirrors `llm.ts`'s auth),
  returns the parsed `GradeResult` stamped `grader:'llm'`; throws on failure.
- `src/lib/progress.ts` — `recordLabSubmission` returns the inserted row `id`
  (additive change from `void`); new `saveGrade(submissionId, result, status)`
  updates that row's `rubric_scores` (= `result`), `grader`, and `status`
  (owner-update RLS already exists).

**Flow in `Lab.tsx` (revised — Save → grade → Continue):**
1. `recordLabSubmission(...)` → row `id` (`status='submitted'`). The work is saved
   immediately and is safe even if the learner leaves.
2. If `config.rubric` exists: do **not** call `onComplete` yet (it would advance
   the cursor and unmount the lab). Show "Grading your work…", call
   `requestLlmGrade`, then `saveGrade(id, result, 'reviewable')` and render the
   result card. On any grading failure: leave the row `submitted` and show a
   quiet "grading unavailable — your work is saved" note.
3. The result card (and the failure note) include a **Continue** button that
   calls `onComplete()` to advance — so the learner sees their anchor-scored
   feedback, then chooses to move on. Continue appears whether grading succeeded
   or failed, so **completion never depends on grading**.
4. If `config.rubric` is absent: call `onComplete()` immediately (the original
   one-click save-and-complete, unchanged).

## 6. Auto-key grader + learner display (§3)

**`src/lib/grading/autoGrade.ts`** (pure):
```ts
autoGrade(answers: Record<string, number>, key: { id: string; label: string; correct: number }[]): GradeResult
```
Per key anchor: `score = 2` if `answers[id] === correct`, else `0`; `max = 2`;
`grader:'auto'`; `overall`/`maxOverall` summed. Unit-tested. **Shipped but not
wired to a cell** (no keyed lab exists yet) — the ready path future keyed labs use.

**Learner display (in `Lab.tsx`).** After grading resolves, an anchor-scored
result card below the output: overall `{overall}/{maxOverall}`, a per-anchor list
(label, score/max, rationale), and a clear **"Provisional — pending review"**
label (LLM grades are `reviewable`). "Grading your work…" while in flight; the
quiet non-blocking note on failure. Styled like existing result cards.

## 7. Testing & verification (§4)

- **Unit (Vitest):**
  - `autoGrade` — all-correct → full marks; a wrong answer → that anchor `0`;
    correct `overall`/`maxOverall`; `grader:'auto'`.
  - **verdict parse/validate helper** (extracted from the `grade` function, Deno-agnostic,
    runs under Vitest like the `chat-core` tests): valid JSON → totals; malformed
    JSON → error; missing anchor / out-of-range score → error.
- **Migration replay:** `npx supabase db reset` clean; cell 2.1's
  `lab_config_json.rubric` has the four anchors; `kind`/`brief`/`title` intact.
- **Lint/build:** `npm run lint` clean; `npm run build` succeeds (Node 22).
- **In-app (Playwright, demo user; needs the `grade` function served + an
  Anthropic key):** unlock Stage 2, open 2.1, run a prompt, **Save & complete** →
  submission inserts and completes instantly; the grade card appears with
  per-anchor scores + "Provisional — pending review"; DB shows the
  `lab_submissions` row updated with `rubric_scores`, `grader='llm'`,
  `status='reviewable'`. *(If no local Anthropic key: verify the save/complete
  path + the "grading unavailable" fallback, and rely on the unit tests for the
  judge logic — note the limitation, as in P4.1.)*
- **Existing suites** stay green; exercises and other cells untouched.
