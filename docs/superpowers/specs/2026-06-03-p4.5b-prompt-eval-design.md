# P4.5b — "Reusable-prompt eval" Lab (cell 2.10)

**Phase:** P4.5b — *An LLM-graded prompt-engineering exercise on cell 2.10 ("Test-driven and constraint-first prompting"). The learner writes ONE reusable, constraint-first prompt, runs it live (streamChat) against a small seeded test set including an edge case, then submits the prompt + its per-case outputs to the P4.2 LLM-judge for an anchor-scored verdict. Practice, not a gate.*
**Depends on:** P4.1 (the `lab_config_json` content-as-data lab pipeline), P4.2 (#48 — the `{brief, sections[]}` LLM-judge + `GradeResultCard`), P4.4b (#52 — the `VoiceEdit` `streamChat` + `AbortController` streaming pattern), P3.6/P3.7 (the render-above-the-quiz exercise pattern).
**Date:** 2026-06-03
**Branch:** `feat/p4.5b-prompt-eval`

## 1. Goal

Add an LLM-graded prompt-engineering exercise to cell 2.10 ("Test-driven and constraint-first
prompting") that drills the lesson's core idea: **constraint-first prompting** = state the rules
(length, format, must-include, must-exclude) *before* you ask; **test-driven prompting** = judge each
result against those rules, across several inputs, instead of eyeballing one output. A good reusable
prompt also **holds on edge cases** (e.g. a record with a missing field) — it flags the gap rather
than inventing data.

The learner:

1. reads a recurring task + the constraints to encode + a small seeded test set (2 complete records +
   1 edge case = a record with a missing income field),
2. writes a **single reusable, constraint-first prompt**,
3. **runs that prompt against each test input live** (Claude via `streamChat`, one call per case) and
   reviews the outputs,
4. **submits**; the P4.2 LLM-judge scores the prompt + its outputs across the cases against a 4-anchor
   rubric, and the anchor-scored result renders in place.

This is **LLM-graded practice that records a `lab_submission` but does NOT gate completion.** Cell 2.10
is `type:'content'` with a 3-question inline quiz; the **quiz stays the completion gate** (same pattern
as the #48 critique, #50 calibration, #51 synthesis, #52 voice-edit, #53 context-diagnostic — render
above the quiz, never call `onComplete`).

**Out of scope:** the grading engine / judge itself (reuse the #48 `requestLlmGrade({brief, sections})`
+ `GradeResultCard` as-is); the streaming seam (reuse `streamChat`); the quiz gate; champion-review
UI/RLS (P5.1); any change to other cells (they must stay byte-stable and their tests green).

## 2. Reuse decision — a new component, reusing every seam

Unlike P4.5a (which reused `ScenarioExercise` wholesale), this exercise has a genuinely new *shape* —
**one prompt fanned out across N live runs, then a single multi-section grade** — so it gets a new
component, `PromptEval.tsx`. But it **reuses every existing seam** rather than re-creating any of them:

| Concern | Reuse |
|---------|-------|
| Streaming a model run | `streamChat(messages, {model, signal}, onChunk)` from `src/lib/llm.ts` — one call per test case. |
| Stream lifecycle | `Lab.tsx` / `VoiceEdit.tsx`'s `AbortController` ref + unmount cleanup (`useEffect(() => () => abortRef.current?.abort(), [])`). |
| Recording the run | `recordLabSubmission(user.id, { labId, transcript, status })` from `src/lib/progress.ts`. |
| Grading | `requestLlmGrade({ rubric, submission: { brief, sections } })` from `src/lib/grading.ts` (the #48 judge). |
| Persisting the grade | `saveGrade(id, result, 'reviewable')` from `src/lib/progress.ts`. |
| Rendering the verdict | `GradeResultCard` from `src/components/GradeResultCard.tsx`, as-is. |
| Model selector | the `CLAUDE_MODELS` / `DEFAULT_MODEL_ID` select from `Lab.tsx` / `VoiceEdit.tsx`. |
| Completion semantics | **Practice, not a gate.** Props are `{ config, labId }` only — no `onComplete` (structurally not a gate; the inline quiz stays the gate). |

| Decision | Choice |
|----------|--------|
| New component vs. reuse `VoiceEdit` | **New component.** `VoiceEdit` is a single generate→revise→grade flow; this is a write-once-prompt → run-N-cases → grade-all flow with a per-case output collection and a "all cases run" submit gate. Different state shape; sharing would bend `VoiceEdit` out of shape. It still reuses every *seam* `VoiceEdit` uses. |
| Grade input shape | The #48 `{ brief, sections[] }` — `brief = brief.instruction`; `sections = [the prompt] + one section per case (INPUT + OUTPUT)`. No judge change. |
| Submit gate | "Submit for grading" is disabled until **every** test case has a collected output (you can't grade outputs you haven't produced). |
| Seed | One migration `20260603060000_seed_lab_config_2_10.sql` (timestamp after #53's `20260603050000`), `where cell_id='2.10' and lab_config_json is null`, `status='in_review'`, `version=version+1`, `updated_at=now()`. Idempotent across `db reset`. |

`src/components/exercises/PromptEval.tsx` — new component:

- Shows the brief + constraints (chips, like `VoiceEdit`) + the seeded test set with the **edge case
  visibly marked** (a badge) + a labelled textarea for the learner's reusable prompt + a model select.
- **"Run against test cases"** → for EACH `testCase`, in sequence, `streamChat([{ role:'user', content:
  `${prompt}\n\n---\nInput:\n${tc.input}` }], { model, signal }, onChunk)`, collecting each case's
  output into `outputs[tc.id]`. Mirrors `Lab`/`VoiceEdit`'s `AbortController` + unmount cleanup. Runs
  sequentially (the chat function is rate-limited per user) — ~3 cases = ~3 calls.
- **"Submit for grading"** (gated until every case has an output) →
  `recordLabSubmission(user.id, { labId, transcript: { kind:'prompt-eval', prompt, outputs }, status:'submitted' })`
  → `requestLlmGrade({ rubric, submission: { brief: brief.instruction, sections: [{ label:"The learner's
  reusable prompt", text: prompt }, ...testCases.map(c => ({ label:`Case: ${c.label}`, text:`INPUT:\n${c.input}\n\nOUTPUT:\n${outputs[c.id]}` }))] } })`
  → `saveGrade(id, result, 'reviewable')` → `GradeResultCard`.
- **No `onComplete`.** Grading failure is a quiet, non-blocking note (the run is saved).
- a11y: labelled textarea; `aria-live` on the running / grading / result regions; per-case output
  announced as it streams.

## 4. Content — the task, test set, answer key (synthetic; `status:'in_review'`)

> **Authoring bar (`docs/content-guide.md`):** no AI-isms; realistic civic-tech context (benefits
> intake), consistent with the existing cells. Inputs are **synthetic** (authored here), so **factual
> risk is low** — but the edge case must *genuinely* stress the prompt. The task is deliberately
> **DISTINCT from the lesson's weekly-status example**: a reusable "raw benefits-intake record →
> standard 3-line case summary for the team queue" prompt. The edge case (a record with a missing
> income field) mirrors the cell's quiz Q3 (the model that guesses a blank income) without handing the
> learner the quiz answer verbatim.

### Brief — the recurring task
**instruction:** "Your team turns raw benefits-intake records into a standard short summary for the
shared case queue. Write ONE reusable, constraint-first prompt that does this for any record — state
your rules before the task, then run it against the test records below and check each result against
those rules."

**constraints (shown as chips):**
- "Exactly 3 lines; about 60 words or fewer."
- "Must include the case ID, the action needed, and the deadline."
- "Must not invent missing data — flag the gap instead (e.g. \"income not provided — follow up\")."
- "Plain language; no internal jargon."

### Test set (2 normal + 1 edge)

**Case 1 — normal — `snap-2231` ("SNAP recertification — complete record")**
```
Case ID: SNAP-2231
Program: SNAP recertification
Household: 4 people
Reported monthly income: $2,840
On file: two recent pay stubs, current lease
Required action: verify the lease address against the utility bill on file
Deadline: recertification packet due 2026-07-15
```

**Case 2 — normal — `med-4417` ("Medicaid renewal — complete record")**
```
Case ID: MED-4417
Program: Medicaid renewal
Applicant: single adult, age 63
Reported monthly income: $1,510
On file: photo ID, prior-year tax return
Required action: confirm continued disability status from the case file
Deadline: renewal due 2026-08-01
```

**Case 3 — EDGE (`isEdge: true`) — `ccap-3902` ("Child care assistance — MISSING income")**
note: "Edge case: the income field is blank. A good prompt makes the model flag the gap, not guess a
number."
```
Case ID: CCAP-3902
Program: Child Care Assistance (CCAP)
Household: 3 people, two children, two earners
Reported monthly income: [left blank on the form]
On file: application form, one pay stub for ONE of the two earners
Required action: collect the second earner's income documentation
Deadline: eligibility determination due 2026-07-22
```

### Answer key (what a strong submission looks like)

- **Constraints stated up front:** the prompt opens with its rules — length/format (3 lines, ≈≤60
  words), the must-include set (case ID, action, deadline), the must-exclude rule (never invent missing
  data — flag it), and plain language — *before* the task and the record. Ideally one good/bad example.
- **Format on the normal cases (1 & 2):** each output is ~3 lines / ≤~60 words, in plain language, and
  contains the case ID, the action needed, and the deadline.
- **Edge case (3) handled correctly:** because income is blank, the output **flags the gap** — e.g.
  "income not provided — follow up" / "income: not reported" — and does **NOT** invent a dollar figure.
  This is the case that separates a reusable, constraint-first prompt from one that passes only the
  clean inputs.
- **Reusable / general:** the prompt is written as general rules that apply to *any* intake record (it
  references "the record" / "the case", not the specific values of one record) — not hardcoded to
  SNAP-2231's numbers. A learner who pasted one record's values into the prompt fails this anchor.

### Rubric anchors (4, judge-scored 0/1/2)

| id | label | description |
|----|-------|-------------|
| `constraints-up-front` | States its constraints up front | The prompt states the rules before the task: length/format **and** the must-include set **and** the must-exclude rule (don't invent missing data). |
| `format-on-normal` | Outputs meet the format on the normal cases | On the two complete records, each output is ~3 lines / ≤~60 words in plain language and includes the case ID, the action needed, and the deadline. |
| `handles-edge-case` | Handles the missing-field edge case | On the record with a blank income field, the output flags the gap ("not provided / follow up") instead of inventing an income figure. |
| `reusable-general` | The prompt is reusable, not hardcoded | The prompt is written as general rules for any intake record, not tailored to one record's specific values. |
