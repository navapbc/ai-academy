# P5.2a — Aggregation layer (dashboard metrics)

**Item:** Phase 5 slice P5.2a (first slice of P5.2 Live dashboard).
**Date:** 2026-06-13 · **Branch:** `feat/p5.2a-aggregation-layer`
**Depends:** P5.1c champion/admin read policies (merged, #75), P5.1b cohort substrate
(merged, #74). Per the Phase 5 build order, P5.2a is the next slice after the P5.1
foundation.

## Goal

Provide the SQL aggregation layer the staff dashboard (P5.2b shell, P5.2c
drill-down) reads from: completion %, score distribution, GLAT pass rate, and
review-queue counts — **all scoped by the P5.1c RLS boundary** so a champion sees
only their cohort, an admin sees all, and a plain learner sees only their own.

SQL-only slice: one migration adding RLS-scoped views + a gated integration test.
No UI (P5.2b/c). Like P5.1c, the deliverable is as much the gated test proving the
boundary as the views themselves.

## The architectural fork

The four metrics group by cohort, which means reading `enrollments`. P5.1c
deliberately left `enrollments` / `cohort_champions` owner-only and **explicitly
punted cross-user enrollment reads to "P5.2/P5.5a"** (see its migration comment and
design spec). So P5.2a is where that deferred work lands.

A `security_invoker` view that `GROUP BY`s `cohort_id` reads `enrollments` as the
*caller*; under a champion's current RLS that returns only the champion's own
enrollment row, collapsing cohort grouping. Two ways out:

- **(a)** A `SECURITY DEFINER` aggregation that re-filters internally. Rejected: it
  forks the boundary into function bodies — one missing scope predicate leaks
  everything, and the existing RLS suite can no longer prove the boundary by itself.
- **(b, chosen)** `security_invoker = true` views **+ add champion/admin SELECT
  policy on `enrollments`**, reusing `is_admin()` / `is_champion_of(user_id)`
  verbatim. Keeps one boundary, in RLS, proven by the same test pattern; this is the
  sanctioned place P5.1c sent the work.

## Design

### 1. `enrollments` SELECT policies (additive)

Two new permissive `SELECT` policies for `authenticated`, verbatim parallel to the
four P5.1c added to the activity tables (owner-read policy untouched):

```sql
create policy "Enrollments are readable by admin"
  on public.enrollments for select to authenticated
  using (public.is_admin());

create policy "Enrollments are readable by champion"
  on public.enrollments for select to authenticated
  using (public.is_champion_of(user_id));
```

`cohort_champions` gets **no** new policy — no view groups by champion, and
`is_champion_of` reads it internally as a `SECURITY DEFINER`. Keep the surface
minimal; add only what a view reads.

### 2. Three `security_invoker = true` views

`security_invoker = true` (PG15+, Supabase-recommended; their linter flags
non-invoker views over RLS tables) means base-table RLS applies as the *querying*
user. The filter applies **pre-aggregation**, so a champion's `count`/`avg` covers
only their cohort — no leak through the aggregate. Each view gets
`grant select ... to authenticated` (parallel to P5.1c's EXECUTE-grant; without it
PostgREST 401s even with RLS correct).

**`learner_progress_summary`** — one row per visible learner; spine is `profiles`
(scoped by P5.1c's `is_champion_of(id)` / `is_admin()`), `left join enrollments`
for `cohort_id`. Per-learner columns:

| Column | Definition |
|---|---|
| `user_id` | `profiles.id` |
| `cohort_id` | from `enrollments` (NULL if unenrolled) |
| `modules_completed` | count of `module_progress` rows `status='completed'` whose `module_id` is a `published` module |
| `modules_total` | count of `modules` where `status='published'` (same scalar for all rows) |
| `completion_pct` | `modules_completed::numeric / nullif(modules_total, 0)` (0–1) |
| `quizzes_attempted` | distinct `module_id` with any `quiz_attempts` row |
| `quizzes_passed` | distinct `module_id` with a passing `quiz_attempts` row |
| `avg_quiz_pct` | mean over modules of the **best** attempt's `score::numeric / nullif(max_score,0)` |
| `glat_passed` | `exists(quiz_attempts where module_id='2.14' and passed)` |
| `reviewable_labs` | count of `lab_submissions` where `status='reviewable'` |

Serves P5.2c drill-down and is the building block for the rollups.

**`cohort_progress_summary`** — aggregates `learner_progress_summary` by
`cohort_id`. Columns: `cohort_id`, `learner_count`, `avg_completion_pct`,
`glat_pass_rate` (`glat_passed` learners / `learner_count`), `avg_quiz_pct`,
`reviewable_total` (sum of `reviewable_labs`). A view selecting a
`security_invoker` view stays invoker end-to-end, so RLS still resolves to the
caller. These are the four P5.2b summary cards.

**`cohort_score_distribution`** — per `(cohort_id, band)` learner counts over
`avg_quiz_pct`, bands `<60` / `60–79` / `80–100` (documented in the migration).
The histogram for P5.2b. Learners with no quiz data (`avg_quiz_pct` NULL) are
excluded from the bands.

### GLAT assumption (P4.10 not built)

`glat_passed` reads `quiz_attempts where module_id='2.14' and passed` — consistent
with every other quiz, returns 0 until P4.10 lands, trivially correct when it does.
**Documented as an explicit assumption** with a `-- revisit when P4.10 lands` comment:
D7 says the GLAT sets a *completion marker*, which could instead land as a
`module_progress` completion. Decision (2026-06-13): include now, returning 0.

### Views, not RPCs

The DoD says "views/RPCs". Views suffice: no parameters needed — cohort filtering is
a `WHERE cohort_id = …` on the view, scoped by RLS; the dashboard reads them via
PostgREST (`public` schema → auto-exposed). RPCs would add a definer surface we
explicitly avoided in the fork.

## Tests (gated `RUN_DB_TESTS=1` + live stack + service-role key)

`src/lib/dashboardAggregation.integration.test.ts`, mirroring
`championAdminRls.integration.test.ts` (service_role seeds cohorts/activity and sets
roles; the W2-2 trigger permits service_role role changes). Triple-gated → SKIPs on a
plain `npm run test`; runs in CI's `db-tests` job.

Negatives are the real proof of scoping:

1. **Champion of cohort A sees A but NOT cohort B** across all three views (the test
   distinguishing a scoped boundary from a broken one).
2. **Admin** sees all cohorts in the rollups.
3. **Regression:** a plain learner reads only their own row from the views (no leak
   through the aggregates).
4. New `enrollments` policy: champion reads in-cohort enrollments, not other
   cohorts'; admin reads all (parallel to the P5.1c enrollment-adjacent assertions).
5. **Correctness:** against known seeded data, `completion_pct` and `glat_pass_rate`
   compute correctly (admin or service_role read of a fully-known fixture).
