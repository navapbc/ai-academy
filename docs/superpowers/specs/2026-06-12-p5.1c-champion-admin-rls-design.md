# P5.1c — Champion/admin read policies

**Item:** Phase 5 slice P5.1c (third foundation slice of P5.1 Roles & RLS).
**Date:** 2026-06-12 · **Branch:** `feat/p5.1c-champion-admin-rls`
**Depends:** P5.1b cohort substrate (merged, #74), P5.1a server-side role assignment (merged, #73).

## Goal

Expand the owner-only SELECT RLS on `module_progress`, `quiz_attempts`,
`lab_submissions`, and `profiles` so that:

- a **champion** can read rows belonging to learners **in a cohort they are
  assigned to** (and only those), and
- an **admin** can read **all** rows,

while the existing owner-only read and the existing write policies are left
untouched (a plain learner still reads only their own rows).

This is the security boundary the rest of Phase 5 (P5.2 dashboards, P5.5
review queue) is gated on, so the deliverable is as much the gated test suite
proving the boundary as the policies themselves.

## Design

### Two `SECURITY DEFINER` helper functions

Both are `stable`, `security definer`, `set search_path = ''`, and
schema-qualify every reference.

- `public.is_admin()` → boolean: the calling user's profile has `role = 'admin'`.
- `public.is_champion_of(target uuid)` → boolean: the calling user is assigned
  (`cohort_champions`) to a cohort that `target` is enrolled in (`enrollments`).

**Why `SECURITY DEFINER`:** the policies on `profiles` reference `is_admin()`;
if the helper read `profiles` under the *caller's* RLS it would re-trigger those
policies → infinite recursion. The functions are owned by `postgres`, which owns
the tables and bypasses RLS (no table uses `FORCE ROW LEVEL SECURITY`), so the
helper reads cleanly. `auth.uid()` inside a definer function still resolves from
the request JWT — it is the *caller's* uid, not the owner's — so the scoping is
correct.

### Additive SELECT policies (owner policy stays)

For each of the four tables, two new permissive `SELECT` policies for
`authenticated` (PostgreSQL OR-combines permissive policies, so the existing
owner policy is preserved):

- `… readable by admin` → `using (public.is_admin())`
- `… readable by champion` → `using (public.is_champion_of(<owner col>))`

The owner column is `user_id` on the three activity tables and `id` on
`profiles`.

### Scope discipline

- **Only** the four named tables get new policies. No read policy is added to
  `enrollments` / `cohort_champions` — `is_champion_of` reads them internally as
  a definer, so the boundary needs no direct grant; enumerating cohort members
  is a P5.2/P5.5a dashboard concern.
- `role_changes` admin-read is **deferred to P5.2** (where a dashboard actually
  consumes it), per that table's migration comment.

## Tests (gated `RUN_DB_TESTS=1` + live stack + service-role key)

Negatives are the real proof of *scoping*:

1. **Champion of cohort A CANNOT read a learner in cohort B** (the test that
   distinguishes a scoped policy from a broken helper) — across all four tables.
2. A champion with **no** cohort assignment reads nothing beyond their own.
3. **Regression:** a plain learner still cannot read another learner's rows.
4. Positives: a champion reads an in-cohort learner's progress/quiz/lab/profile;
   an admin reads across cohorts.

Champion/admin/cohort setup uses the `service_role` pattern from
`adminRole.integration.test.ts` (service_role sets `profiles.role` and writes the
cohort substrate; the W2-2 trigger permits service_role role changes).
