# P5.2d — Realtime staff dashboard (design)

**Date:** 2026-06-16
**Plan task:** P5.2d (Phase 5, Live dashboard). Depends on P5.2b.
**Status:** approved, implementing.

## Goal

Upgrade the staff cohort dashboard from manual-reload to **live auto-refresh**: when
the underlying progress data changes, the dashboard refetches itself without the staff
user clicking Retry. The DoD (PROJECT-PLAN P5.2d) is simply "Supabase realtime
subscription — ship P5.2b/c on polling first; this is the live upgrade."

## Constraints / context

- The dashboard renders the P5.2a aggregation **views** (`cohort_progress_summary`,
  `cohort_score_distribution`) plus the P5.2c roster (`learner_progress_summary`).
- Supabase `postgres_changes` fires only on **base-table** rows, not views. The four
  base tables feeding the views are `module_progress`, `quiz_attempts`,
  `lab_submissions`, `enrollments`.
- All four already have RLS (owner + P5.1c champion/admin reads). Realtime respects RLS
  for `postgres_changes`, so a subscriber only receives events for rows it can read.
- The test harness has **no realtime** by design (`src/test/setup.ts` only polyfills a
  WebSocket so the client constructs; "we never use realtime in tests").

## Decisions (brainstormed 2026-06-16)

- **Update strategy: trigger-refetch (debounced).** Subscribe to base-table changes; on
  any event, debounce ~500 ms then call the existing `reload()` to refetch the
  RLS-scoped views. **Payloads are ignored** — no incremental aggregate math, no row
  data read client-side, no drift risk, no leak surface.
- **No interval-poll backstop.** Rely on realtime for liveness plus the existing manual
  Retry button. (Realtime auto-reconnects.) Matches "ship on polling first; this is the
  live upgrade."

## Design

### 1. Migration — `supabase/migrations/20260616000000_realtime_dashboard_publication.sql`

Add `module_progress`, `quiz_attempts`, `lab_submissions`, `enrollments` to the
`supabase_realtime` publication. Idempotent: a `DO` block that checks
`pg_publication_tables` before each `ALTER PUBLICATION ... ADD TABLE`, so it survives
`supabase db reset`. No new policy or view — RLS is inherited from P5.1c/P5.2a.

> **Known limitation (scoped roles):** INSERTs (new completions / quiz attempts / lab
> submissions — the dominant signal) deliver under RLS without extra config. DELETE/UPDATE
> need `REPLICA IDENTITY FULL` for RLS to evaluate the OLD row — and this lands
> *specifically* on champions, because `is_champion_of(user_id)` reads a column on the
> changed row whereas `is_admin()` ignores columns (an admin gets every event regardless).
> So a deletion / un-enrollment may not auto-deliver to a champion until the next
> foreground load. Any delivered event triggers a refetch regardless, and the refetch is
> RLS-scoped, so this is an under-delivery latency edge, never a leak — not worth a schema
> change now, but tracked here rather than waved off.

### 2. New module — `src/lib/dashboardRealtime.ts`

- `debounce(fn, ms)` — small pure helper returning a callable with a `.cancel()` method;
  coalesces a burst of calls into one trailing call. Unit-tested.
- `subscribeToDashboardChanges(onChange: () => void): () => void`
  - Returns a **no-op disposer when `!isSupabaseConfigured`** (graceful offline/unconfigured
    degrade).
  - Otherwise opens one channel (`dashboard-changes`) with a `postgres_changes`
    listener (`event: '*'`, `schema: 'public'`) for each of the four tables, wired to a
    **debounced** `onChange`. `.subscribe()`s and returns a disposer that **cancels the
    pending debounce timer** (so a queued refresh can't fire after unmount) **and** calls
    `supabase.removeChannel(channel)`.

### 3. `src/lib/useDashboard.ts`

Refactor the fetch into a single stable `load({ background })` callback (mounted-ref
guarded):

- **Foreground** (`background: false`) — mount load + manual Retry: toggles `loading`,
  sets `error` on failure (the current behaviour).
- **Background** (`background: true`) — realtime-triggered refresh: **never toggles
  `loading` and never sets `error`** — on failure it logs and keeps the stale data, so a
  live update can't flip the staff viewer's whole screen to a spinner or to the error
  screen mid-session. A successful background refresh clears any prior error.

One `useEffect` subscribes via `subscribeToDashboardChanges(() => load({ background: true }))`
on mount and disposes on unmount. `reload` stays the foreground path (Retry button
unchanged).

> **Why:** realtime → `reload()` verbatim would run `setLoading(true)` on every learner
> event, flashing the full-page spinner; a transient refetch error would wipe good data
> to the error screen. The background path keeps liveness smooth.

## Testing

- Unit: `debounce` coalesces a burst into a single trailing call after the window;
  `.cancel()` prevents a pending call from firing.
- Unit: `subscribeToDashboardChanges` against a fake Supabase client (mock
  `./supabaseClient`) — registers a listener for each of the four tables, an incoming
  event triggers the (debounced) callback, the disposer cancels the timer and calls
  `removeChannel`, and it returns an inert no-op (never touching the client) when
  Supabase is unconfigured.
- Unit (`useDashboard`): a background refresh updates data **without** entering the
  loading state, and a failed background refresh keeps the prior data (no error screen).
- `CohortDashboard.test.tsx` **mocks `../../lib/dashboardRealtime`** so the subscription
  is a deterministic no-op. (Required, not optional: `.env` sets `VITE_SUPABASE_URL`, so
  `isSupabaseConfigured` is `true` under vitest — the env guard alone would let the real
  client open a websocket in the component test.)
- Realtime **delivery** (the websocket round-trip + RLS auth on the socket) is validated
  by a live browser smoke as the seeded admin — the smoke must show an actual auto-update
  (make a completion in session B, watch session A's card update *without* clicking
  Retry), not merely that the page loads. If no event arrives, the socket isn't
  authenticated as the user (RLS evaluates as `anon` → zero events) and needs
  `supabase.realtime.setAuth()`.

## Verification

`npm run lint && npm test && npm run build` on Node 22. Browser smoke: open the staff
dashboard, complete a module / submit a lab in another session, watch the affected
card / roster auto-update with zero console errors.

**Result (2026-06-16):** verified for BOTH staff roles. Admin (sees-all) and a temp
champion assigned to the demo cohort each saw AVG COMPLETION auto-update 0%→50% on a
direct DB completion with no Retry click, zero console errors. The champion case is the
load-bearing one: `is_admin()` is row-independent so an admin never exercises RLS
*scoping*; the champion smoke confirms `is_champion_of(user_id)` evaluates correctly
inside Realtime's WAL RLS check.

## Out of scope

Incremental client-side aggregation, interval polling, broadcast-from-DB triggers,
learner-dashboard realtime (P5.3), review-queue realtime (P5.5).
