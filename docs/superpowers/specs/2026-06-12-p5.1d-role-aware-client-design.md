# P5.1d — Role-aware client

**Item:** Phase 5 slice P5.1d (final foundation slice of P5.1 Roles & RLS).
**Date:** 2026-06-12 · **Branch:** `feat/p5.1d-role-aware-client`
**Depends:** P5.1c champion/admin read policies (merged, #75), P5.1b cohort
substrate (#74), P5.1a server-side role assignment (#73).

## Goal

A `useRole` hook + a client route guard so that admin/champion views are
**reachable and gated**: a champion/admin can navigate into a staff area, and a
learner has no path to it. This is the last foundation slice before the real
staff features (P5.2 dashboards, P5.3 learner self-view, P5.5 review queue),
which slot into the seam this establishes.

The actual dashboards are out of scope — the staff view here is a placeholder
that only proves the access plumbing works.

## Design

### `useRole` (`src/lib/useRole.ts`)

Reads the signed-in user's `profiles.role` (owner-read RLS already lets a user
read their own profile, so the anon key suffices). Returns
`{ role, loading, error, isAdmin, isChampion, isStaff }`.

Two deliberate choices, both about **not reintroducing the D-01 class of bug**
(un-keyed state leaking across a user switch on a shared browser):

- **No localStorage cache.** Unlike progress, a stale role is a privilege
  hazard. The role is fetched fresh per session.
- **Consumed inside the `key={session.user.id}` subtree** (`Academy`), which
  already remounts per user — mirroring how `useProgress` is scoped — so role
  state resets cleanly on sign-out/sign-in.

**Fail-closed everywhere:** `role` is `null` while loading and on any read
error, so a transient failure never grants elevated access. `isStaff` is
`admin || champion`.

This only decides which views the client *offers*; the real data boundary is
the champion/admin read RLS from P5.1c. The server never trusts this value.

### `RoleGuard` (`src/components/RoleGuard.tsx`)

`{ role, loading, allow: Role[], children, fallback? }`. Renders `children` only
when the resolved role is in `allow`; shows a spinner while loading and a
"staff access only" notice otherwise. Delegates the decision to a pure exported
`isAllowed(role, allow)` (null never passes). The `allow` list is the seam for
the eventual admin-only vs champion split (P5.2 dashboard vs P5.5 review).

### Wiring (`App.tsx`, `Sidebar.tsx`)

- A third top-level `View` (`'learning' | 'playground' | 'staff'`, in
  `types.ts`). The staff branch in the content region is wrapped in
  `RoleGuard allow={['admin','champion']}` rendering a placeholder `StaffArea`.
- The Sidebar gains a **Staff** entry rendered only when `isStaff` — so a
  learner has no UI path to the view. The `RoleGuard` is the backstop if the
  `staff` view is reached some other way.

There is no router in this app (views are state); extending the `View` union is
the established convention.

## Tests

- **`RoleGuard.test.tsx`** — allowed role renders children; disallowed renders
  the notice; loading shows the spinner (no content); null fails closed; custom
  fallback honoured. Plus `isAllowed` unit cases.
- **`useRole.test.tsx`** (supabase + auth mocked) — admin/champion/learner
  resolve with correct flags; a read error fails closed; signed-out makes no
  query and grants no role.
- **`Sidebar.test.tsx`** — the DoD's "learners can't reach them" path: a learner
  sees **no** Staff entry; a staff user sees it and clicking it navigates to the
  `staff` view.

## Notes / follow-ups

- The seeded demo user is a `learner`, so the positive (staff) path is proven by
  the role-mocked tests. To eyeball it, promote a profile via the P5.1a
  `admin-set-role` Edge Function (or a service_role update); not a blocker.
- **Local test runner needs Node 22** — jsdom 29 pulls parse5 v8 (ESM) and
  `require(esm)` only works on Node ≥22 (CI already uses Node 22). On Node 20 the
  jsdom suites error with `ERR_REQUIRE_ESM`. Reinforces the still-open W1
  `.nvmrc` item.
- An end-to-end learner-negative spec (no new seed needed) is a cheap future
  add; the Sidebar component test already covers that path.
