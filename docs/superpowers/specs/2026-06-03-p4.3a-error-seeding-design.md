# P4.3a — "Error-seeding" Lab (cell 1.2)

**Phase:** P4.3a — *A "spot the confabulation" exercise on cell 1.2: the learner audits a polished AI-drafted artifact claim-by-claim, marking each SUPPORTED vs FABRICATED/UNVERIFIABLE. AUTO-GRADED against an answer key (no LLM). Practice, not a gate.*
**Depends on:** P3.6/P3.7 (the render-above-the-quiz auto-graded exercise pattern: `DataClassifier`, `FailureSpotter`, the pure-grader + `.test.ts` convention, `recordLabSubmission`). **Independent of P4.2/P4.3b** — no LLM judge, no shared grading code.
**Date:** 2026-06-03
**Branch:** `feat/p4.3a-error-seeding`

## 1. Goal

Add a new interactive exercise — **OutputAudit** — where the learner reads a polished,
realistic AI-generated civic-tech artifact and audits it **claim-by-claim**, marking each
discrete claim **Supported** (verifiable / correctly stated) or **Fabricated /
unverifiable** (a confabulation, or uncheckable from the document alone). It is
**AUTO-GRADED against a deterministic answer key — no LLM call.** It is the deterministic
sibling of P4.3b's `critique` (which uses the P4.2 LLM-judge).

This is **graded practice that records a `lab_submission` but does NOT gate completion**.
Cell 1.2 is `type:'content'` with an inline quiz; the **quiz stays the completion gate**
(same pattern as the P3.6/P3.7 exercises — render above the quiz, never call `onComplete`).

Wired on one cell:
- **1.2 "Hallucination as a structural feature, not a bug"** — audit a polished AI *Housing
  Choice Voucher notice* whose authority reads clean but is seeded with a mix of supported
  and fabricated claims.

**Out of scope:** the P4.2 LLM judge / `GradeResultCard` (untouched — this is deterministic);
champion-review UI/RLS (P5.1); retrofitting other cells; matrix Stages 3–4; any change to the
quiz gate, the `chat`/`grade` functions, or other exercise components.

## 2. Context (current state)

- **The auto-graded exercise pattern** (`DataClassifier`, `FailureSpotter`): a self-contained
  component that renders an artifact via `ReactMarkdown + remarkGfm`, takes per-item input,
  **auto-grades against a key on Submit**, reveals each item's `why`, records a
  `lab_submissions` row, and **does not accept `onComplete`** — completion is structurally the
  quiz's job. The grading logic lives in a **pure, unit-tested grader** (`scenarioSorter.grade.ts`,
  `harmRubric.grade.ts` + `.test.ts`).
- **`ModuleRenderer.renderExercise()`** dispatches on `module.labConfig.kind`; the inline quiz
  renders after and gates. New kinds are added as additive `LabConfig` union members + a switch
  case (FE-06 guards a missing case with a visible fallback).
- **`recordLabSubmission(userId, { labId, transcript, status })`** (`src/lib/progress.ts`)
  inserts an append-only, RLS-owner-only row with a free-form `transcript`. Auto-graded
  exercises tag the transcript by `kind` and store `score`/`maxScore`.
- **Content lives in two places:** lesson/quiz come from `curriculum-content.json` (seeded
  early); **lab configs come from migrations** (e.g. `…_seed_lab_config_*.sql`). Cell 1.2 has
  body+quiz but **no `lab_config_json`** yet.
- **Cell 1.2 is Stage 1b**, which is **never locked** (only Stage 2 is gated on Stage 1a), so
  it is reachable immediately after sign-in.

## 3. Decisions

| # | Decision | Choice |
|---|----------|--------|
| D1 | New exercise vs. extend an existing one | **New `OutputAudit` component + `OutputAuditConfig` union member.** Additive; no other component or config changes. |
| D2 | Grading | **Deterministic auto-grade, no LLM.** A pure grader `outputAudit.grade.ts` compares each per-claim verdict to the answer-key `status`. This is the explicit contrast with P4.3b's LLM-judged critique. |
| D3 | Completion semantics | **Practice, not a gate.** `OutputAudit` takes **no `onComplete`**; the inline quiz remains the gate (P3.6/P3.7 pattern). Records a `lab_submissions` row `transcript.kind:'output-audit'`, `status:'submitted'`. |
| D4 | Verdict vocabulary | Two values: **`supported`** (verifiable / correctly stated) and **`fabricated`** (confabulated *or* unverifiable-from-the-document). One control = one binary judgment per claim, matching the lesson's "trust vs. verify" framing. |

| D6 | Content grounding | The artifact **cannot recite cell 1.2's own worked example** (a fake court case + fake regulation citation in a benefits-appeal legal memo) — that would hand learners the answer. Nor P4.3b's SNAP/Medicaid material. Use a **different, web-verified** domain: **Housing Choice Voucher (24 CFR Part 982)** (see §6). |
| D7 | Seed | One migration `20260603010000_seed_lab_config_1_2.sql`, `where cell_id='1.2' and lab_config_json is null`, `status='in_review'`, `version=version+1`. Idempotent across `db reset`. Timestamp clears both main's latest migration (`20260602270000`) **and** P4.3b's `20260603000000`, so no collision regardless of merge order. |

## 4. Types, grader, component, dispatch

`src/types.ts` — additive union member (other members untouched):

```ts
/** A learner's per-claim verdict; also the answer-key value. */
export type AuditStatus = 'supported' | 'fabricated';

export interface OutputAuditConfig {
  kind: 'output-audit';
  intro?: string;
  artifact: { label: string; bodyMd: string };  // the polished AI artifact under audit
  claims: {
    id: string;
    text: string;            // a discrete, checkable claim drawn from the artifact
    status: AuditStatus;     // answer key ('fabricated' = confabulated/unverifiable)
    why: string;             // shown after grading
  }[];
}
// added to: export type LabConfig = … | OutputAuditConfig;
```

`src/components/outputAudit.grade.ts` — **pure** grader (no React, unit-tested):
`gradeOutputAudit(picks, claims)` → `{ results: {id, picked, correct}[], correctIds, score,
total, allCorrect }`. A claim is correct when `picks[id] === claim.status`; a missing pick is
incorrect (recorded as `picked: null`).

`src/components/exercises/OutputAudit.tsx` — renders the artifact (`ReactMarkdown + remarkGfm`),
the optional `intro`, and each claim with a Supported / Fabricated radiogroup. On Submit:
auto-grade via `gradeOutputAudit`, reveal each claim's `why` + the correct answer, show
`You scored N / M`, and `recordLabSubmission(user.id, { labId, transcript: { kind:'output-audit',
answers, score, maxScore }, status:'submitted' })`. Accessible controls
(`role="radiogroup"`/`role="radio"`/`aria-checked`, `role="status" aria-live="polite"` feedback,
`role="alert"` save error, `sr-only` correct/incorrect annotations) matching the sibling
exercises. **No `onComplete` prop.** A "Try again" reset mirrors the siblings.

`ModuleRenderer.renderExercise()` — add `case 'output-audit': return <OutputAudit
config={module.labConfig} labId={module.cellId} />;` (+ the dispatch test case + mock).

## 5. The artifact (cell 1.2)

A polished AI-drafted **Housing Choice Voucher — Eligibility & Next Steps notice** for a
caseworker to forward to a family. It reads authoritative and correctly attributes the program
to 24 CFR Part 982, but is seeded with a mix of supported and fabricated claims (full text in
the seed migration; answer key in §6).

**Why this artifact (not the lesson's):** the 1.2 lesson already walks through a *fake court
case + fake regulation citation in a benefits-appeal legal memo*. Reusing that gives away the
answer. We use a **different, real** domain — the Housing Choice Voucher program — and a
**different mix of confabulation types** (an invented dollar figure, a real-citation/fabricated-
deadline, an unsourced statistic) rather than a single fake case. Distinct from P4.3b's SNAP
(7 CFR 273.10) / Medicaid (42 CFR 435.916) material too.

## 6. Content — the ANSWER KEY (web-verified)

> Authoring bar (`docs/content-guide.md`): no AI-isms; realistic civic-tech context; every
> factual claim grounded. **The provisions cited are real and described accurately; the
> fabricated claims are defensible confabulations (an invented figure, a real-citation/
> fabricated-deadline, and an unsourced statistic) — never accidentally true.** Sources
> verified 2026-06-03 against eCFR / Cornell LII, HUD.gov, and the Federal Register.

7 claims · **4 supported / 3 fabricated.**

| # | id | Claim (as audited) | Answer | Ground truth + source |
|---|----|--------------------|--------|------------------------|
| 1 | `authority` | "The HCV program is administered by the PHA under **24 CFR Part 982**." | **SUPPORTED** | Real. 24 CFR Part 982 ("Section 8 Tenant-Based Assistance: Housing Choice Voucher Program") is the governing regulation, administered by PHAs. https://www.ecfr.gov/current/title-24/subtitle-B/chapter-IX/part-982 |
| 2 | `tenant-share` | "A participant generally pays the **highest of 30% of monthly adjusted income** or 10% of monthly gross income (total tenant payment)." | **SUPPORTED** | Real. The TTP "highest of" formula is **24 CFR § 5.628** (30% of adjusted income, 10% of gross, or the minimum); family share = gross rent − HAP (§ 982.515). Stated accurately (adjusted, not gross). https://www.law.cornell.edu/cfr/text/24/5.628 |
| 3 | `payment-standard` | "The **federal payment standard for a two-bedroom unit is fixed at $1,850 per month nationwide**." | **FABRICATED** | Confabulated figure. No national flat dollar standard exists. Under **24 CFR § 982.503** the PHA sets the payment standard locally at **90–110% of the area's published FMR** — varies by area/unit size, changes annually. The specific national number is unverifiable and contradicts the rule. https://www.law.cornell.edu/cfr/text/24/982.503 |
| 4 | `inspection` | "The agency must inspect the unit **before the HAP contract** and **re-inspect at least every two years** during assistance." | **SUPPORTED** | Real. **24 CFR § 982.405** requires an initial inspection before the HAP contract and inspections **at least biennially**. (Anchored on the inspection *timing*, which is unaffected by the HQS→NSPIRE naming transition that completes Feb 1, 2027.) https://www.law.cornell.edu/cfr/text/24/982.405 |
| 5 | `portability` | "The family may use the voucher to lease in **another jurisdiction** that operates a voucher program (portability)." | **SUPPORTED** | Real. "Portability" under **24 CFR §§ 982.353 / 982.355** lets a family lease outside the issuing PHA's jurisdiction anywhere an HCV program operates. https://www.law.cornell.edu/cfr/text/24/982.353 |
| 6 | `hearing-deadline` | "Under **24 CFR § 982.555(c)**, a household must request an informal hearing **within 14 calendar days** of a termination notice." | **FABRICATED** | Confabulated deadline on a real citation. The hearing right is real (§ 982.555), but the section sets **no day-count — "14 days" appears nowhere in it.** Subsection **(c) ("Notice to family")** only requires the PHA *to state* a deadline; the actual number is set by the PHA's **administrative plan**, not the CFR. Citing § 982.555(c) as the source of a fixed federal 14-day deadline misstates it. https://www.law.cornell.edu/cfr/text/24/982.555 |
| 7 | `lease-up-stat` | "Our agency **leases up 91% of issued vouchers within 60 days, well above the national average of 69%**." | **FABRICATED** | Unverifiable. No source; uncheckable from the notice. Lease-up / success rates are PHA- and year-specific (and "utilization" vs. "success rate" are different metrics); real data comes from HUD's **VMS/PIC** systems and HUD PD&R research, not a fixed published constant. https://www.huduser.gov/portal/publications/Using-HUD-Administrative-Data-to-Estimate-Success-Rates.html |

**Framing grounded in NIST AI 600-1:** confabulation (colloquially "hallucination") is a
structural property of generative models — "confidently stated but erroneous or false content"
— enumerated as a GenAI risk category, **not a rare bug.** So a fluent, confident citation /
figure / deadline is exactly what you must verify. NIST AI 600-1 (July 2024):
https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf (DOI 10.6028/NIST.AI.600-1).

**Content caveats (for the SME reviewer):**
- Claim 2 is phrased "highest of 30% of **adjusted** income or 10% of gross" — keep "adjusted"
  (writing only "30% of income" or "gross" would itself be a subtle error).
- Claim 4 is anchored on the **inspection timing** (§ 982.405), not the HQS-vs-NSPIRE name, so
  the key doesn't age out when the NSPIRE compliance date hits **Feb 1, 2027**.
- `status='in_review'` pending SME sign-off.
