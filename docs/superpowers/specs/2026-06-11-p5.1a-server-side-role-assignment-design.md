# P5.1a — Server-side role assignment (Edge Function + admin bootstrap)

**Item:** Phase 5 slice P5.1a (the first foundation slice of P5.1 Roles & RLS).
**Date:** 2026-06-11 · **Branch:** `feat/p5.1a-server-side-role-assignment`
**Depends:** P1.5 (auth/profiles), W2-2 (#68, the `prevent_self_role_change` trigger).

## The problem

`profiles.role` (`learner` | `champion` | `admin`) is the key the rest of Phase 5 will gate on
(champion/admin RLS in P5.1c, the staff dashboard in P5.2). But W2-2 (#68) installed a
`BEFORE UPDATE` trigger, `prevent_self_role_change`, that raises `42501` whenever the `role`
column changes and `current_user` is not `service_role`/`supabase_admin`/`postgres`. That closed
the privilege-escalation hole (D-06) but also means **no PostgREST/authenticated path can set any
role at all** — so there is currently no way to make someone a champion or admin, and a fresh DB
has zero admins (chicken-and-egg: granting admin requires being admin).

P5.1a builds the only sanctioned write path: a server-side (`service_role`) Edge Function that an
admin calls to set another user's role, plus an env-based bootstrap so the first admin can exist.

## Approach (A, chosen)

A Supabase Edge Function using the `service_role` client — mirrors the existing `chat`/`grade`
functions. Rejected alternatives: a Postgres `SECURITY DEFINER` RPC (pushes admin-authorization
and env-allowlist logic into SQL, hard to unit-test); DB-only/manual promotion (undocumented
tribal knowledge, declined during brainstorming).

## Components

### 1. Edge Function `supabase/functions/admin-set-role/index.ts`
Mirrors `chat`/`grade` for CORS allow-list, POST-only, and per-user rate limiting.

- **Authn:** build an anon client with the caller's `Authorization` header, `getUser()` — a bare
  anon key is not a user token, so it 401s. Then require `@navapbc.com` (403 otherwise).
- **Authz — caller must be admin:** caller is admin iff their email is in the
  `BOOTSTRAP_ADMIN_EMAILS` env allowlist **OR** their `profiles.role === 'admin'` (read with the
  service_role client). Otherwise 403.
- **Request body:** `{ targetEmail: string, role: 'learner' | 'champion' | 'admin' }`. The target
  is identified by **email** (admins operate in emails; the app is domain-restricted) and resolved
  to a profile id server-side via the service_role client. 404 if no such profile.
- **Guardrails:**
  - Validate `role` is one of the three enum values (400 otherwise).
  - **Block self-demotion:** if `targetId === callerId` and `role !== 'admin'`, reject (422). This
    stops an admin stripping their own admin in one click while still permitting self-*promotion*
    (which is the bootstrap mechanic — see below).
- **Write:** set `profiles.role` for the target via the **service_role** client (this is what the
  W2-2 trigger permits), then insert one `role_changes` audit row.
- **Response:** `{ ok: true, targetId, oldRole, newRole }`, or a structured `{ error }` with the
  status above.

### 2. Pure logic `supabase/functions/admin-set-role/admin-core.ts` (+ `admin-core.test.ts`)
Deno-agnostic, unit-tested under vitest/node exactly like `chat-core`/`verdict`:
- `parseSetRoleRequest(raw): { ok: true, value } | { ok: false, error }` — validates body shape +
  role enum + non-empty email.
- `isAllowlistedAdmin(email, csv): boolean` — parses/normalizes the comma-separated env allowlist
  (trim, lowercase, ignore blanks).
- `isSelfDemotion(callerId, targetId, newRole): boolean` — the guardrail predicate.
- CORS/domain helpers (reuse `chat-core` shapes, or inline as `grade` does).

### 3. Migration `<timestamp>_role_changes_audit.sql`
```
create table public.role_changes (
  id           uuid primary key default gen_random_uuid(),
  actor_id     uuid not null references auth.users (id) on delete set null,
  actor_email  text,
  target_id    uuid not null references auth.users (id) on delete cascade,
  target_email text,
  old_role     text,
  new_role     text not null,
  created_at   timestamptz not null default now()
);
alter table public.role_changes enable row level security;
-- No permissive policy: locked down like content_versions. Only service_role
-- writes/reads; an admin-read policy arrives with P5.1c / the P5.2 dashboard.
```
(`actor_id` is `on delete set null` so the audit row survives if the actor is later deleted;
`target_id` cascades with the user.)

### 4. Gated integration test `src/lib/adminRole.integration.test.ts` (`RUN_DB_TESTS=1`)
Mirrors `rls.integration.test.ts` (skips when no live stack / flag). Asserts the security boundary
at the DB layer:
- An **authenticated** client doing `update profiles set role='admin'` on its own row is rejected
  with `42501` (the W2-2 trigger holds).
- The **service_role** client setting `profiles.role` **succeeds** and the row reflects the new
  role (the path the function uses).
- The **service_role** client can insert a `role_changes` row; a non-service client cannot read it
  (locked-down RLS).

The function's request/authz/guardrail logic is covered by the `admin-core` unit tests (the
vitest DB job does not serve Edge Functions, so end-to-end HTTP is exercised manually / left to a
later E2E pass).

### 5. Env
Add `BOOTSTRAP_ADMIN_EMAILS=` (comma-separated) to `supabase/functions/.env.example` with a
comment. `SUPABASE_URL` / `SUPABASE_ANON_KEY` / `SUPABASE_SERVICE_ROLE_KEY` are auto-injected into
Edge Functions by the Supabase runtime — no manual wiring.

## Bootstrap flow
An operator puts their `@navapbc.com` email in `BOOTSTRAP_ADMIN_EMAILS`. They call `admin-set-role`
targeting **themselves** with `role: 'admin'`. Authorized via the allowlist; self-*promotion* is
allowed (only self-demotion is blocked); their `profiles.role` is now `admin`, which is what
P5.1c's RLS keys on. The allowlist remains the durable break-glass set for recovery.

## Out of scope (YAGNI / later slices)
- **No client UI** — invoking this from the app is P5.1d (role-aware client) / P5.5a (cohort mgmt).
  No unused client helper is added now.
- **No champion/admin read RLS** on `profiles` or the user tables — that's P5.1c.
- **No last-admin-removal guard** — the env allowlist is the recovery path (decided in brainstorm).
- **No cohort scoping** — P5.1b introduces cohorts; this function sets a flat role.
