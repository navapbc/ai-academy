# P5.1b — Cohort substrate (cohorts + enrollments + champion assignments)

**Item:** Phase 5 slice P5.1b (second foundation slice of P5.1 Roles & RLS).
**Date:** 2026-06-11 · **Branch:** `feat/p5.1b-cohort-substrate`
**Depends:** P1.3 (local stack), P1.5 (auth/profiles). Built on top of P5.1a (merged, #73).

## The problem

P5.1c will scope RLS so a **champion sees the learners in their cohort** and an **admin sees
all** — but there is no cohort concept in the schema yet. The cohort substrate is therefore a
hard prerequisite for P5.1c, which is why D11's slice pulled it forward from P5.5 into P5.1b.
This slice adds only the tables, their baseline RLS, a local demo seed, and tests — no UI (P5.5a)
and no champion/admin cross-user read policies (P5.1c).

## Decisions (from brainstorming)

- **One cohort per learner**, DB-enforced via `unique(user_id)` on `enrollments`.
- **Champions are many-to-many** with cohorts via a dedicated `cohort_champions` join table
  (a champion can oversee several cohorts; a cohort can have co-champions).
- **Three explicit tables** (approach A) rather than one unified `cohort_members` table, so P5.1c
  can give learners vs. champions distinct read scopes cleanly.
- **Demo cohort data lives in `supabase/seed.sql`**, not a migration — the demo user (`…0001`) only
  exists via `seed.sql` (local), so a migration enrolling it would fail in cloud/prod. Migrations
  stay environment-independent (DDL only).

## Components

### 1. Migration `<timestamp>_cohort_substrate.sql` — DDL + baseline RLS only

```sql
create table public.cohorts (
  id         uuid primary key default gen_random_uuid(),
  name       text not null,
  created_by uuid references auth.users (id) on delete set null,
  created_at timestamptz not null default now()
);

create table public.enrollments (
  id          uuid primary key default gen_random_uuid(),
  cohort_id   uuid not null references public.cohorts (id) on delete cascade,
  user_id     uuid not null references auth.users (id) on delete cascade,
  enrolled_by uuid references auth.users (id) on delete set null,
  enrolled_at timestamptz not null default now(),
  unique (user_id)                       -- one cohort per learner (DB-enforced)
);
create index on public.enrollments (cohort_id);

create table public.cohort_champions (
  id          uuid primary key default gen_random_uuid(),
  cohort_id   uuid not null references public.cohorts (id) on delete cascade,
  user_id     uuid not null references auth.users (id) on delete cascade,
  assigned_by uuid references auth.users (id) on delete set null,
  assigned_at timestamptz not null default now(),
  unique (cohort_id, user_id)            -- a champion assigned once per cohort; many cohorts allowed
);
create index on public.cohort_champions (user_id);
```

**RLS** (enable on all three; mirror existing patterns):
- `cohorts` — RLS on; **authenticated may SELECT** (cohort names aren't sensitive and
  learners/dashboards need them — same posture as the `modules` table). No insert/update/delete
  policy.
- `enrollments` — RLS on; **owner SELECT own** (`auth.uid() = user_id`) so a learner sees their
  own cohort. No write policy.
- `cohort_champions` — RLS on; **owner SELECT own** (`auth.uid() = user_id`) so a champion sees
  which cohorts they're assigned to. No write policy.

All writes happen via migrations/seed and the future admin path (P5.5a, using the service_role
pattern from P5.1a). Admin-all and champion-scoped cross-user reads are intentionally **not** here
— they arrive in P5.1c with the `is_admin` / `is_champion_of` helper functions.

### 2. Seed — `supabase/seed.sql` (local demo data, appended after the existing demo rows)
- One `Demo Cohort` row with a fixed UUID.
- Enroll the demo learner (`00000000-0000-0000-0000-000000000001`) into it.
- Idempotent: fixed UUIDs + `on conflict do nothing`; the enrollment is guarded so it no-ops if the
  demo profile is absent. (Lives in `seed.sql` alongside the demo user's existing progress/quiz
  rows; never references the demo user from a migration.)

### 3. Gated integration test `src/lib/cohorts.integration.test.ts` (`RUN_DB_TESTS=1`)
Mirrors `rls.integration.test.ts` (skips without the flag + a live stack; service-role-key gate
where needed). Asserts the baseline boundary:
- A signed-up learner, after a **service_role** enrollment, can SELECT their own `enrollments` row;
  a second learner cannot see it.
- `cohorts` is SELECT-able by an authenticated user.
- An authenticated client **cannot** INSERT into `cohorts`, `enrollments`, or `cohort_champions`
  (no write policy → the insert returns an RLS error / affects zero rows).
- The **service_role** path can create a cohort, enroll a user, and assign a champion.
- `enrollments.unique(user_id)` rejects a second enrollment for the same user (one-cohort rule).

## Out of scope (later slices)
- **No UI** — cohort/enrollment management + champion assignment is P5.5a.
- **No admin-all / champion-scoped read policies** on these tables or the user tables — P5.1c
  (with the `is_admin` / `is_champion_of` SECURITY DEFINER helpers).
- No soft-delete/archive, no cohort `slug`, no enrollment status/history beyond the single row.

## Tests / definition of done
- `npx supabase db reset` ×2 (idempotent), then `RUN_DB_TESTS=1 npm test` fully green incl. the new
  `cohorts.integration.test.ts`; the existing suites stay green and the non-flagged run still skips.
- `npm run lint` + `npm run build` green.
- Studio shows the `Demo Cohort` with the demo learner enrolled after a reset.
