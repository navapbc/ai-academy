# P3.9 — Interactive: Harm Scenario + Sign-off (cells 1.12, 1.13)

**Phase:** P3.9 — *Civic-tech harm rubric + role self-classification & sign-off checklist.*
**Depends on:** P3.2 (content-as-data — merged), and follows the exercise pattern from P3.6 (#23) / P3.7 (#25).
**Date:** 2026-06-02
**Branch:** `feat/p3.9-harm-scenario-signoff`

## 1. Goal

Add two interactive exercises following the established content-as-data exercise
pattern:

- **1.12 — Civic-tech harm rubric:** a graded exercise where the learner reads
  civic-tech scenarios and classifies each into one of four harm patterns.
- **1.13 — Role self-classification + sign-off checklist:** an ungraded
  commitment exercise where the learner picks the role that best fits how they're
  involved with AI and signs off on a set of responsible-use commitments.

Both are **supplementary practice** that record a `lab_submission`; module
completion stays with each cell's existing inline quiz. Content is **drafted by
Claude for later SME review** (`status='in_review'`), as in P3.4–P3.7.

Out of scope: changing completion gating, clearing the cells' quizzes, other
cells, a schema migration, drag-and-drop.

## 2. Context (current state)

- **Exercise pattern (P3.6 #23, P3.7 #25):** interactive exercises are config
  objects on the `LabConfig` discriminated union (keyed by `kind`), stored in the
  `modules.lab_config_json` column and surfaced as `module.labConfig`. Components
  live in `src/components/exercises/`, take `{ config, labId }`, grade locally,
  call `recordLabSubmission(user.id, { labId, transcript, status })`, and **do
  not** call `onComplete` — completion is left to the cell's inline quiz.
  `ModuleRenderer` dispatches them via `renderExercise()` (a switch on
  `module.labConfig?.kind`), rendered between the lesson and the inline quiz.
  Reference implementation: `src/components/exercises/FailureSpotter.tsx`.
- **`recordLabSubmission(userId, { labId, transcript, status })`** in
  `src/lib/progress.ts` inserts into `lab_submissions` (owner-only RLS;
  `transcript` is `unknown` jsonb), throwing on error.
- **Cells 1.12 and 1.13** are both `type='content'` with an authored lesson
  (`body_md`) and an inline quiz (`quiz_json`) that gates completion. The 1.12
  lesson defines exactly the four harm patterns used here (errors-at-scale,
  automation bias, opacity/explainability, exclusion/digital divide).
- **The `lab_config_json` column already exists** (P3.2.3b) — no schema change is
  needed; adding new `kind`s is purely additive in TypeScript + seed data.

## 4. Data model & types (§1)

Two new members on the `LabConfig` union in `src/types.ts` (no DB schema change —
new `kind`s stored in the existing `lab_config_json`):

```ts
// 1.12 — civic-tech harm rubric: classify each scenario into one harm pattern.
export interface HarmRubricConfig {
  kind: 'harm-rubric';
  patterns: { id: string; label: string; desc: string }[]; // rubric, shown + the MC options
  scenarios: { id: string; text: string; correct: string; why: string }[]; // correct = pattern id
}

// 1.13 — role self-classification + sign-off checklist (ungraded commitment).
export interface SignoffConfig {
  kind: 'signoff-checklist';
  intro?: string;
  roles: { id: string; label: string; desc: string }[];
  commitments: { id: string; text: string }[];
}
```

Both added to `export type LabConfig = … | HarmRubricConfig | SignoffConfig;`.
`mapRowToModule` already surfaces `lab_config_json` as `module.labConfig`; no
mapping change needed.

## 5. Components & wiring (§2)

Both in `src/components/exercises/`, props `{ config, labId }`, FailureSpotter
card style, recording a submission and **not** calling `onComplete`.

**`HarmRubric.tsx`** (1.12) — graded, single MC per scenario:
- Renders the four `patterns` as a labeled rubric reference (label + desc).
- Each `scenario`: text + the four patterns as MC option buttons. State
  `picks: Record<scenarioId, patternId>`.
- "Submit answers" (enabled when all assigned) → grade via the pure
  `gradeHarmRubric(picks, scenarios)` helper, reveal correct/incorrect + `why`
  per scenario and an "n / N correct" score, then
  `recordLabSubmission(user.id, { labId, transcript: { answers, score, maxScore }, status: 'submitted' })`.
  "Try again" resets. Same grade/feedback/save/retry flow as FailureSpotter.

**`SignoffChecklist.tsx`** (1.13) — ungraded commitment:
- Role single-select (radio-style buttons, `aria-checked`) with each role's `desc`.
- Commitments as checkboxes.
- "Sign off" enabled only when a role is selected **and every commitment is
  checked** → `recordLabSubmission(user.id, { labId, transcript: { role, acknowledged: commitmentIds, signedAt: ISO }, status: 'submitted' })`;
  then a "Signed off" confirmation state with an "Edit / re-sign" affordance. No
  scoring, no `onComplete`.
- Both guard `if (!user)` with the FailureSpotter "sign in to record" message;
  save failures surface a non-blocking error and leave the UI usable.

**`ModuleRenderer` wiring** — add two cases to the existing `renderExercise()`
switch (`module.labConfig?.kind`), plus the two imports:

```tsx
      case 'harm-rubric':
        return <HarmRubric config={module.labConfig} labId={module.cellId} />;
      case 'signoff-checklist':
        return <SignoffChecklist config={module.labConfig} labId={module.cellId} />;
```

No change to `renderInteractive`, the complete-button logic, or the inline-quiz
gate. 1.12/1.13 stay `type='content'`; the exercise renders between the lesson
and the quiz, exactly like 1.7.

## 6. Seed content (§3) — drafted for SME review

One new migration (timestamped after the latest, `…210000`) sets
`lab_config_json` and `status='in_review'` for 1.12 and 1.13. **It does not touch
`body_md`, `quiz_json`, or `type`** — lessons and quizzes are preserved.

**1.12 — harm rubric.** Four patterns (from the 1.12 lesson):
`errors-at-scale`, `automation-bias`, `opacity`, `exclusion`. **Five
civic-tech scenarios**, each mapping to one pattern (one pattern repeated for
variety) — e.g. a mis-coded statewide eligibility rule denying a category
overnight (errors-at-scale); a caseworker rubber-stamping a borderline "deny"
(automation-bias); a denied applicant told only "the system flagged it"
(opacity); an English-only, bandwidth-heavy intake dropping rural/limited-English
applicants (exclusion). Each scenario has a one-to-two-sentence `why`.

**1.13 — role self-classification + sign-off.**
- **Roles** (pick best fit): commission/scope AI work · review or approve AI
  outputs · make decisions informed by AI · procure/contract for AI tools ·
  oversee a team or program that uses AI.
- **Commitments** (all checked to sign off), tied to Stage 1 themes: ask whether
  a human meaningfully reviews AI-influenced decisions; insist on an explanation a
  denied person could understand; verify tools handling regulated data are
  approved for that data class; ask who's accountable when the AI is wrong and how
  far errors could spread; ask whether the hardest-to-serve can use the process;
  raise concerns rather than defer to a confident output.
- Short intro: you don't have to build AI to be responsible for how it's used.
