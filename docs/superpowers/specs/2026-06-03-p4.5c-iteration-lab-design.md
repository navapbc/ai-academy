# P4.5c — "Iteration-log scorer" Lab (cell 2.4)

**Phase:** P4.5c — *An LLM-graded MULTI-TURN exercise on cell 2.4 ("Iteration as the literate behavior"). The learner conducts a real multi-turn refinement conversation with Claude toward a constrained goal, then submits the whole conversation; the P4.2 judge scores the QUALITY OF THE LEARNER'S ITERATION (their steering turns), not the final output. Practice, not a gate.*
**Depends on:** P4.1 (the `lab_config_json` content-as-data lab pipeline), P4.2 (#48 — the `{brief, sections[]}` LLM-judge + `GradeResultCard`), P4.4b/P4.5b (#52/#54 — the `VoiceEdit`/`PromptEval` `streamChat` + `AbortController` streaming pattern), P3.6/P3.7 (the render-above-the-quiz exercise pattern).
**Date:** 2026-06-03
**Branch:** `feat/p4.5c-iteration-lab`

## 1. Goal

Add an LLM-graded **multi-turn** exercise to cell 2.4 ("Iteration as the literate behavior") that drills
the lesson's core idea: **iteration = treating an AI conversation as a loop, not a vending machine.** You
send a starter, read the output critically, refine or push back, and repeat — each turn carrying forward
what you learned. The lesson's evidence: iteration shows up in ~86% of effective conversations; a weak
first draft is the normal starting point, not a tool failure.

The learner:

1. reads a goal + a couple of demanding constraints the first output commonly misses,
2. conducts a **real multi-turn refinement conversation** with Claude (each turn sends the growing
   `messages[]` array via `streamChat`), steering the draft toward the goal,
3. once they've taken at least `minTurns` turns, **submits the whole conversation**,
4. the P4.2 LLM-judge scores **the quality of the learner's iteration** — their steering turns — against
   a 4-anchor rubric, and the anchor-scored result renders in place.

**KEY DESIGN PRINCIPLE — grade the learner's turns, not the model's output.** The live model is
non-deterministic and may produce a good first draft, so grading the final artifact would be unreliable
and would miss the point. The rubric and the judge's sections focus on the learner's refining turns:
specificity, building across turns, stress-testing / catching a weakness, and recognizing "done." This is
robust regardless of how good the model's responses happen to be.

This is **LLM-graded practice that records a `lab_submission` but does NOT gate completion.** Cell 2.4 is
`type:'content'` with a 3-question inline quiz; the **quiz stays the completion gate** (same pattern as
#48 critique, #50 calibration, #51 synthesis, #52 voice-edit, #53 context-diagnostic, #54 prompt-eval —
render above the quiz, never call `onComplete`).

**Out of scope:** the grading engine / judge itself (reuse the #48 `requestLlmGrade({brief, sections})` +
`GradeResultCard` as-is); the streaming seam (reuse `streamChat`, which already takes a `messages[]`
array); the quiz gate; champion-review UI/RLS (P5.1); any change to other cells.

## 2. Reuse decision — a new multi-turn component, reusing every seam

Every existing lab is **single-turn**. This one is genuinely new in shape: it accumulates a `messages[]`
array (`[user, assistant, user, assistant, …]`) and sends the **growing array** to `streamChat` each
turn, with a small chat-style UI and a minimum-turns gate before submit. So it gets a new component,
`IterationLab.tsx` — but it **reuses every existing seam**:

| Concern | Reuse |
|---------|-------|
| Streaming a model turn | `streamChat(messages, {model, signal}, onChunk)` from `src/lib/llm.ts` — it **already takes a `messages[]` array**, so the multi-turn history is sent as-is each turn. |
| Stream lifecycle | `Lab.tsx` / `VoiceEdit.tsx`'s `AbortController` ref + unmount cleanup (`useEffect(() => () => abortRef.current?.abort(), [])`). |
| Recording the run | `recordLabSubmission(user.id, { labId, transcript, status })` from `src/lib/progress.ts`. |
| Grading | `requestLlmGrade({ rubric, submission: { brief, sections } })` from `src/lib/grading.ts` (the #48 judge). |
| Persisting the grade | `saveGrade(id, result, 'reviewable')`. |
| Rendering the verdict | `GradeResultCard`, as-is. |
| Model selector | the `CLAUDE_MODELS` / `DEFAULT_MODEL_ID` select. |
| Completion semantics | **Practice, not a gate.** Props are `{ config, labId }` only — no `onComplete`. |

| Decision | Choice |
|----------|--------|
| New component vs. reuse `VoiceEdit`/`PromptEval` | **New component.** Those are single-turn (generate→revise, or one prompt→N runs). This is a true back-and-forth conversation with an accumulating history and a turn gate — a different state shape. It still reuses every *seam*. |
| What gets graded | **The learner's turns**, via the judge `sections`: (1) the goal, (2) the learner's turns in order (user messages only), (3) the full transcript for context. The rubric anchors are written about the iteration, not the artifact. |
| Submit gate | "Submit iteration for grading" is disabled until `turnCount >= minTurns` (and not mid-stream). |
| Seed | One migration `20260603070000_seed_lab_config_2_4.sql` (timestamp after #54's `20260603060000`), `where cell_id='2.4' and lab_config_json is null`, `status='in_review'`, `version=version+1`, `updated_at=now()`. Idempotent across `db reset`. |

`src/components/exercises/IterationLab.tsx` — new multi-turn component:

- State: `messages: ChatMessage[]` (committed `{role, content}` turns), `input`, `isStreaming`,

  status:'submitted' })` → `requestLlmGrade({ rubric, submission: { brief: brief.instruction, sections:

  `saveGrade(id, result, 'reviewable')` → `GradeResultCard`.
- **No `onComplete`.** Grading failure is a quiet, non-blocking note (the conversation is saved).
- a11y: the conversation renders as a log (`role="log"` + `aria-live="polite"` for new turns); the
  streaming reply is announced (`aria-busy`); the input is a labelled textarea.

## 4. Content — the goal, constraints, answer key (synthetic; `status:'in_review'`)

> **Authoring bar (`docs/content-guide.md`):** no AI-isms; realistic civic-tech context, consistent with
> the existing cells. The source notice is **synthetic** (authored here), so **factual risk is low**. The
> scenario is deliberately **DISTINCT** from the 2.1 SNAP-recertification lab, the 2.6 CCS-notice
> voice-edit, AND the cell 2.4 lesson's own benefits-appeal example: a **benefits OVERPAYMENT notice**.
> The constraints are chosen so the first draft commonly misses something (a specific dollar figure +
> deadline that must survive, a reading level, the appeal/waiver right, "no invented specifics"), so
> iteration is genuinely needed.

### Brief — the goal + the raw notice
**instruction:** "You've received a benefits overpayment notice written in dense agency language. Work
with Claude across a few turns to turn it into a short, plain-language explanation the recipient can act
on. Read each draft critically and steer — the first draft usually misses something. The raw notice:
*\"Notice of Overpayment — Case SNAP-7781. Our records indicate an overpayment of $1,248.00 for the
benefit period January–April 2026, resulting from unreported earned income. You must respond within 30
days of the notice date (notice dated 2026-09-12). You may: (a) repay the balance in full; (b) request a
repayment agreement; or (c) request a waiver or appeal the determination.\"*"

**constraints (shown as chips):**
- "Keep the exact overpayment amount ($1,248.00) and the 30-day deadline (notice dated 2026-09-12)."
- "Sixth-grade reading level; about 150 words or fewer."
- "Must tell the recipient they can request a waiver or appeal."
- "No invented specifics — don't add a phone number, amount, or date that isn't in the notice."

**starter (hint):** "Try a starter like: *\"Rewrite this overpayment notice in plain language for the
person who received it.\"* Then read the reply against the constraints above and steer from there."

**minTurns:** 3

### Answer key — strong vs. weak iteration (this is what the rubric scores)

**Strong iteration** (what a high-scoring conversation looks like):
- **Turn 1:** a reasonable starter ("rewrite this in plain language for the recipient").
- **Turn 2 — specific, targeted:** names the actual gap against a constraint — e.g. *"This dropped the
  30-day deadline. Add the response deadline (within 30 days of 2026-09-12) as the first line, and keep
  the $1,248.00 figure exactly."* (Not "make it clearer.")
- **Turn 3 — builds + tightens:** carries the prior draft forward and adds the next unmet constraint —
  e.g. *"Good. Now bring it to a sixth-grade reading level and under 150 words, without losing the amount
  or the deadline."*
- **Turn 4 (or a later turn) — stress-tests / catches a weakness** (cell 2.4's core move): *"Critique
  your own draft — what could a stressed reader misread? And confirm the $1,248.00 amount and the
  2026-09-12 deadline are both still present and correct."* — or catches an invented specific ("you added
  a phone number that isn't in the notice; remove it").
- **Done:** the final draft keeps both figures, reads plainly and short, states the waiver/appeal right,
  and invents nothing — and the learner stops once it's met, rather than thrashing.

**Weak iteration** (what scores low):
- Re-asking the same vague thing each turn ("make it better", "clearer", "longer") with no reference to
  the actual draft or the unmet constraints.
- Restarting the goal from scratch each turn instead of building on the prior draft.
- Never checking that the required amount/deadline survived; accepting a draft that dropped the deadline
  or invented a phone number / repayment figure.
- Treating the first answer as final (single turn) — which the `minTurns` gate prevents from even
  submitting, reinforcing the lesson.

### Rubric anchors (4, judge-scored 0/1/2, written about the LEARNER'S TURNS)

| id | label | description |
|----|-------|-------------|
| `specific-targeted` | Refinements are specific and targeted | The learner's turns reference the actual output and the unmet constraints (e.g. "you dropped the $1,248 figure", "still above a sixth-grade level") rather than vague "make it better." |
| `builds-across-turns` | Builds across turns | Each turn carries the work forward toward the goal, keeping what already worked, rather than restarting from scratch or re-asking the same thing. |
| `stress-tests` | At least one turn stress-tests or catches a weakness | A turn asks the model to critique its own answer, checks that a specific claim/figure/constraint survived, or corrects a wrong assumption — cell 2.4's core move. |
| `reaches-goal` | Reaches the goal and recognizes "done" | The final result meets the brief's constraints (exact figures + deadline kept, plain language, waiver/appeal right stated, nothing invented) and the learner recognizes when it's done. |
